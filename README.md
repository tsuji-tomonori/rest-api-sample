# はじめて設計する REST API

椅子の修理をスマートフォンから頼んだ社員が、翌日、受付番号で進み具合を確かめます。画面には何を返せばよいでしょうか。修理を終えたのに、翌朝また「未完了」と表示されたら、どこを調べればよいでしょうか。この教材では、一つの修理受付を題材に、API の設計から公開後の運用までをたどります。

## 対象と読み方

初めて Web API を設計する人向けです。第1〜8章の設計編はプログラミングや AWS の経験がなくても読めます。通信に使う JSON と、仕様書を書く YAML は、初めて登場する箇所で説明します。サンプルを動かすときは Python 3.12 と uv、PostgreSQL まで試すときは Docker Compose を使います。AWS に構築する場合は、アカウントとデプロイ権限が必要です。

| 工程 | 修理依頼の例で分かること | 次に使うもの |
| --- | --- | --- |
| 設計（第1〜8章） | 「登録した依頼をもう一度開きたい」を、入力とレスポンスの約束にする | 操作ごとの設計シート、OpenAPI 仕様書、具体的な期待結果 |
| 開発（第9章） | 件名と場所を検証し、依頼を保存してから、受付番号と取得先を返す | 手元で登録と照会ができるアプリ、コードから生成した仕様書 |
| 構築（第10章） | どの呼び出し元を受け付け、どの関数がどの権限で台帳に接続するかを決める | CDK の構成、DB のテーブル、公開後に確認する URL |
| テスト（第11章） | 取得先を開いて同じ依頼が読めるか、完了状態が DB に残るかを確かめる | 変更ごとの CI 結果、配信先での疎通確認の記録 |
| 運用（第12〜13章） | 依頼を登録・照会できないときに原因を絞り、既存の利用者が使い続けられる形で変更を届ける | 監視指標、障害対応の手順、次の版の設計条件 |

**設計だけ学ぶ場合**は第7章まで読み、[空欄の設計シート](docs/templates/contract-sheet.md)に自分の業務を一つ書きます。第8章には同じシートの別の記入例があります。すでに公開中の API を変える場合は、設計の段階で[第13章の互換性判断](docs/13-versioning.md)も読んでください。

**実装までたどる場合**は、登録した依頼の `Location` を開けるかを各工程で追ってください。テストは開発中から実行します。サンプルの自動配信では、CI に合格した変更を AWS に配置し、そこで初めて確認できる権限と接続を実際の URL で確かめます。用語は[用語集](docs/glossary.md)から引けます。

## サンプルで試せること

教材の **サンプルで試せる** は、このリポジトリのコードで確かめられる例です。次の5操作を実装しています。受付番号には登録レスポンスの `id` が入ります。

| 操作 | リクエスト | 成功時に確かめること |
| --- | --- | --- |
| 修理を依頼する | `POST /repair-requests` | `201`、受付番号、依頼を開くための `Location` |
| 依頼を探す | `GET /repair-requests?status=open&limit=10` | `200` と一覧。続きがあれば `next_after` |
| 1件を開く | `GET /repair-requests/{request_id}` | `200` とその依頼の件名・場所・状態 |
| 完了にする | `PATCH /repair-requests/{request_id}` | `200` と変更後の依頼 |
| 誤登録を取り除く | `DELETE /repair-requests/{request_id}` | `204`、本文なし。その番号を再び開くと `404` |

**設計例（未実装）** は、業務の条件が変わったときの選択肢です。ログインや `/me`、本人だけが変更できる権限、`ETag` と `If-Match`、二重登録を防ぐキー、入力欄の位置を示す `errors[].pointer`、会議室予約はこちらに含まれます。サンプルは利用を許可した人が同じ台帳を扱う構成です。
