# 第10章　会議室の予約なら、何が変わるか

最後に、[第6章の設計メモ](06-contract.md)を別の仕事に当てはめてみましょう。社員は会議室の予定を調べ、空いていれば予約し、自分の予約を取り消せます。同じ部屋の利用時間が重なるときは、先に受け付けた予約を残します。

10時から11時まで予約がある部屋を思い浮かべてください。別の人が10時30分から予約したときと、11時ちょうどから予約したときで、画面に何を伝えますか。以下は設計の一例です。

## 社員の行動を三つの操作にする

| 社員がしたいこと | 要求の例 | 画面が受け取るもの |
| --- | --- | --- |
| 3番の部屋の予定を見る | `GET /rooms/3/reservations?date=2030-06-12` | `200` と、その日に重なる予約の開始・終了時刻。予約がなければ空の一覧 |
| 3番の部屋を予約する | `POST /rooms/3/reservations` | `201` と予約内容。`Location` に、新しい予約を表す `/reservations/48` などのパス |
| 自分の予約を取り消す | `DELETE /reservations/48` | `204`。その時間帯が空く |

部屋はパスで指定し、登録の本文には `starts_at` と `ends_at` を入れます。開始時刻の例は `2030-06-12T10:00:00+09:00` です。このオフィスでは、予定を調べる `date` の1日を日本時間で区切ります。予約者は認証で確かめた社員から決め、取り消すときはその社員と予約者を照合します。[RFC 3339 §5.6 日時の表記](https://www.rfc-editor.org/rfc/rfc3339.html#section-5.6)

## 時刻の境目と、二人が同時に押した場合を確かめる

「11時に退室したら、次の人が11時に入室できる」と決めます。この一文があれば、受付結果を具体的に予測できます。

| 3番の部屋の状況 | 新しい申込み | 期待する結果 |
| --- | --- | --- |
| 10時〜11時は予約済み | 10時30分〜11時30分 | `409 Conflict`。元の1件を残し、別の時間を選ぶよう案内する |
| 10時〜11時は予約済み | 11時〜12時 | `201 Created`。隣り合う2件の予約になる |
| 13時〜14時は空き | 二人が同時に13時〜14時を選ぶ | 一方が `201`、もう一方が `409`。予約は1件 |

二人の画面に同時に「空き」と表示されることはあります。そこで重なりの判定は、予約を保存するところでも行います。PostgreSQL を使うなら、部屋が同じで時間帯が重なる行を登録できない制約を設ける方法があります。[RFC 9110 §15.5.10 競合](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.10)・[PostgreSQL「時間帯の重複を防ぐ制約」](https://www.postgresql.org/docs/current/rangetypes.html#RANGETYPES-CONSTRAINT)

## 予約の途中で失敗したら、取り消すか、続きから再開するか

予約が確定したら、別のサービスから社員に通知することにします。画面では1回のボタン操作でも、予約を保存する処理と、通知を届ける処理があります。以下は、この業務を広げる場合の設計例です。

### 同じデータベースに保存するものは、一緒に確定する

画面は新しい申込みを始めるときに、申込み1回を識別する**操作キー**を作ります。この例では、予約の `POST` に `Idempotency-Key: booking-8f31` というヘッダーを付けます。応答が届かず同じ申込みを送り直すときも、キーと本文は同じです。サーバーは「社員と操作キー」の組を一意にし、申込内容、予約とその番号、未送信の通知を一つのトランザクションで保存します。トランザクションは、複数の変更を一緒に確定する仕組みです。[PostgreSQL「トランザクション」](https://www.postgresql.org/docs/current/tutorial-transactions.html)・[Amazon Builders’ Library「安全に再試行できる API」](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

| どこで止まったか | データベースに残るもの | 同じ操作キー・同じ内容がもう一度届いたら |
| --- | --- | --- |
| 保存の途中でエラーが起き、確定（コミット）前に取り消した | 今回の変更はすべて元に戻る（ロールバック） | 新たに空きを確かめ、申込みを最初から処理する |
| コミット後、画面へ返す応答が消えた | 予約番号と操作キーが残り、部屋は確保済み | 保存済みの予約番号を返す。2件目は作らない |

この契約では、同じキー・同じ内容の要求が同時に届いても予約を確定するのは一方だけです。もう一方は確定した予約番号を受け取ります。同じキーのまま時間帯を変えた要求には `409` を返します。別の時間を予約するなら新しいキーを使います。キーを保管する期間も、画面が安全に再送できる期間として決めておきます。[Amazon Builders’ Library「同じ識別子で異なる意図が届いた場合」](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

### 外部への通知は、残した記録から再開する

送信担当の処理は、確定済みの「未送信」の記録を読み、外部サービスに通知を頼みます。通知に失敗しても予約は有効です。再試行するのは通知の工程だけです。通知先が受け付けた直後に通信が切れる場合に備え、再送にも同じ通知 ID を使い、受け取り側でも処理済みの ID を照合します。予約と送信予定を同じデータベースで確定するこの方法を、**トランザクショナル・アウトボックス**と呼びます。[AWS「Transactional outbox pattern」](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

もし「外部の手配が成功して初めて予約成立」という要件なら、部屋を仮押さえし、手配が最終的に失敗したときに仮押さえを解除します。すでに確定した操作の効果を、後の操作で打ち消す方法を**補償**と呼びます。処理が長引く場合は `202 Accepted` で受付を返し、この設計では `Location: /operations/81` で進捗の宛先を知らせます。画面は `GET /operations/81` で処理中・完了・失敗を確かめます。受付を再送しても同じ処理 ID が返るようにすると、利用者は途中から追跡できます。[RFC 9110 §15.3.3 受付](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)・[AWS「Saga orchestration pattern」](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/saga-orchestration.html)

### まとめて申し込んだうち、1件だけ失敗したら

研修で午前・午後の両方の部屋を押さえたい場合、午前だけ予約しても研修を開けません。両方の空きを確かめ、同じデータベースで2件を一緒に確定します。午後が埋まっていれば、その申込みで取れた部屋は0件です。

一方、総務が別々の会議を100件取り込むなら、空いていた99件を残すほうが担当者の手間は減ります。たとえば非同期の取込処理を受け付け、結果には各行の受付番号か失敗理由を載せます。担当者は失敗した行だけ直して再登録できます。**途中までの成功を利用者がそのまま使えるか**が、全件をまとめるか、1件ずつ確定するかの判断基準です。[Google AIP-233「一括作成と部分成功」](https://google.aip.dev/233#atomic-vs-partial-success)

予約と通知の例で「同じ申込みを2回送っても予約は1件」という性質が**冪等性**です。「部屋を両方取るか、両方とも取らないか」という性質が**原子性**です。確定済みの予約を保ち、未送信の通知だけを続けるのは、アプリが記録した進捗に基づく**再開**です。メソッドを選んだら、この三つのうち業務に必要な保証を契約に書きます。[RFC 9110 §9.2.2 冪等なメソッド](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)・[RFC 5789 §2 PATCH に求められる原子性](https://www.rfc-editor.org/rfc/rfc5789.html#section-2)

自分の案件でも、まず一つ、利用者の判断が分かれる場面を選んでください。そのときに送る値、返る応答、保存後に残るデータまで書けば、業務の約束をチームで確かめられます。
