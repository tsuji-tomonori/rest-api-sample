# 第5章　HTTP ステータスコードから次の行動を決める

修理依頼の登録ボタンを押したあと、画面には「受け付けました」「件名を入力してください」「しばらくお待ちください」のどれを表示すればよいでしょうか。手掛かりになるのが、HTTP の応答に必ず含まれる3桁の **ステータスコード** です。先頭の数字で結果の大枠が分かります。[RFC 9110 §15 ステータスコード](https://www.rfc-editor.org/rfc/rfc9110.html#section-15)

## ステータスコードの早見表

| 分類 | 応答が伝えること | 呼び出し側の次の行動 |
| --- | --- | --- |
| **2xx　成功** | 要求は成功した。どこまで済んだかは各コードが示す | 返された結果を表示する。受付段階なら進捗を確認する |
| **4xx　要求に関するエラー** | 入力、権限、対象の状態など、この要求に関して処理できない条件がある | コードを基に、入力を直す、権限を確認する、時間を置くなどの対処を選ぶ |
| **5xx　サーバー側のエラー** | サーバーや中継先で要求を処理できなかった | 利用者に状況を伝え、提供側が調査できるよう発生時刻などを控える |
| 1xx　途中経過 | 処理の途中で返る情報。例は `100 Continue` | `100` なら要求の本文を送信し、最終応答を待つ |
| 3xx　転送・再利用 | 結果を得るために追加の対応が要る | 移転先を示す応答なら案内先へ進み、`304 Not Modified` なら保存済みの内容を使う |

コードを選ぶときは、まず**依頼した操作が成功したか**を考えます。成功なら 2xx から選びます。失敗したら、要求に関する条件を示せるか（4xx）、サーバーや中継先で処理が行き詰まったか（5xx）を確かめます。たとえば、予約が埋まっていれば `409` です。利用者が正しく入力していても、予約時点の空き状況によって 4xx は起こります。

## 2xx では、何が終わったかを示す

| コード | このコードを選ぶ場面 | 呼び出し側でできること |
| --- | --- | --- |
| `200 OK` | 照会した1件や一覧、更新後の内容を返す | 本文を表示する。検索結果が0件なら空の一覧として示す |
| `201 Created` | 新しい依頼を保存し、受付番号が決まった | `Location` ヘッダーが示す宛先で作成結果を開く |
| `202 Accepted` | 帳票作成の要求を受け付け、作成はこれから行う | 受付時点の状態を読み、案内された方法で進捗を確認する |
| `204 No Content` | 削除などが完了し、返す本文がない | 本文を読み込まずに一覧を更新する |

修理が来週になる予定でも、今頼んだことが「台帳への登録」なら、保存した時点で `201` です。サンプルでは `Location: /repair-requests/42` のように登録先を知らせます。帳票作成の `202` は受付までを伝えるため、帳票ができたかどうかはその後に確かめます。[RFC 9110 §15.3 成功応答](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3)・[§10.2.2 Location](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.2)

### 同じ内容をもう一度読むとき

修理依頼サンプルは `Cache-Control: no-store` を返し、キャッシュへの保存を禁じています。一方、利用者別の表示設定をブラウザーに保存してよい API なら、`Cache-Control: private, no-cache` を選べます。`private` は共有キャッシュへの保存を禁じ、`no-cache` は保存済みの応答を使う前に、まだ使えるかをサーバーに確認するよう求めます。[RFC 9111 §5.2.2 応答のキャッシュ制御](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2)

1. 初回の `GET /me/preferences` では、サーバーが `200 OK` と設定の本文を返し、その内容を識別する `ETag: "v3"` を添えます。
2. 次回、ブラウザーは同じ宛先への `GET` に `If-None-Match: "v3"` を添えます。同じ版なら `304 Not Modified` が本文なしで返り、保存していた設定を表示できます。設定が変わっていれば、`200 OK` と新しい本文、更新後の `ETag` が返ります。[RFC 9110 §13.1.2 If-None-Match](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.2)・[§15.4.5 304](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4.5)

## 4xx では、何を確かめれば先に進めるかを示す

同じ失敗でも、JSON の書き間違いと、直前にほかの人が会議室を予約した場合とでは、利用者への案内が変わります。次は修理依頼と会議室予約を例にした、一般的な HTTP API の設計例です。[RFC 9110 §15.5 クライアント側のエラー](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5)・[RFC 6585 §4 要求の頻度制限](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)

| コード | 提供側がそのコードを返す場面 | 呼び出し側が次にすること |
| --- | --- | --- |
| `400 Bad Request` | JSON の括弧が閉じていないなど、要求を正しく読めない | JSON の書き方や要求の組み立て方を直す |
| `401 Unauthorized` | 必要な認証情報がない、または期限切れ。提供側は `WWW-Authenticate` で求める認証方式を示す | 指定された方式で有効な認証情報を用意する |
| `403 Forbidden` | 要求は理解したが実行を拒む。例は閲覧専用の利用者による削除 | 許可された操作を選ぶか、必要な権限を確認する |
| `404 Not Found` | 指定した番号の依頼が見つからない。権限上、その存在を伏せる場合にも使える | パスや番号を確かめ、必要なら一覧に戻る |
| `405 Method Not Allowed` | その宛先は指定のメソッドに対応していない。提供側は対応するメソッドを `Allow` に載せる | パスと `Allow` を照合し、目的に合うメソッドを使う |
| `409 Conflict` | 要求が現在の状態と競合する。例は予約枠の重複 | 最新の空きを確認し、別の時間を選ぶ |
| `415 Unsupported Media Type` | JSON を受け付ける操作に CSV が届くなど、送られた形式に対応していない | 本文を対応形式に変え、その形式を `Content-Type` に指定する |
| `422 Unprocessable Content` | 本文の形式・構文は読めるが、値が条件に合わない。例は空白だけの件名 | 指摘された項目の値を直す |
| `429 Too Many Requests` | 短時間に利用上限を超えて要求が届いた | 呼び出す頻度を下げる。`Retry-After` があれば、次に試す時期の目安にする |

修理依頼サンプルでは、未登録の番号への照会は `404` です。一方、未完了の依頼を検索して0件だったときは `200` と `{"items":[],"next_after":null}` を返します。検索自体は成功したので、画面は「未完了の依頼はありません」と案内できます。

## 5xx では、提供側が調べる場所を絞る

5xx を受け取った画面では、利用者に入力し直すよう求めても解決しないことがあります。呼び出し側は、いつ、どの操作で起きたかを記録します。提供側は次の違いから調査を始められます。[RFC 9110 §15.6 サーバー側のエラー](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6)

| コード | 何が起きたか | 提供側が確かめること |
| --- | --- | --- |
| `500 Internal Server Error` | アプリ内で予期しない例外が起きるなど、要求を完了できなかった | 発生時刻に対応するアプリのログと処理箇所 |
| `502 Bad Gateway` | 中継サーバーが、接続先から不正な応答を受け取った | 中継先が返した応答の形式と接続先のログ |
| `503 Service Unavailable` | 過負荷や保守のため、一時的にサービスを提供できない | 負荷や復旧の見込み。次に試せる時期を示せるなら `Retry-After` を返す |
| `504 Gateway Timeout` | 中継サーバーが、接続先から期限内に応答を受け取れなかった | 接続先の処理時間と、中継サーバーの待ち時間 |

`Retry-After: 60` は「次に試すまで60秒待つ」という目安です。4xx や 5xx を受けた操作を再送できるかは、コードとあわせて、その操作を繰り返したときの効果を確かめます。依頼の登録をもう一度送れば、登録が2件になる場合があります。[RFC 9110 §10.2.3 Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)・[第4章　同じ要求を二度送るとどうなるか](04-methods.md)

## エラーの理由を本文で伝える

コードで大枠が分かったら、本文で今回の理由を伝えます。**Problem Details** は、HTTP API のエラーを共通の形で記述する仕様です。サンプルで存在しない依頼を開くと、次のような応答が返ります。ヘッダーは抜粋です。[RFC 9457 §3 エラー本文](https://www.rfc-editor.org/rfc/rfc9457.html#section-3)

```http
HTTP/1.1 404 Not Found
Content-Type: application/problem+json

{"type":"about:blank","title":"Not Found","status":404,"detail":"修理依頼が見つかりません。"}
```

プログラムは実際の HTTP ステータスを使って分岐します。同じコードの問題をさらに区別するときは、種類を示す `type` を読みます。この例の `about:blank` は、HTTP ステータスの意味をそのまま使うという指定です。`title` は種類の短い名前、`detail` は今回の状況を人に伝える説明です。アプリの手前にある API Gateway などが別形式の応答を返すこともあるため、呼び出し側は `Content-Type` を確かめて本文を読みます。[RFC 9457 §3.1](https://www.rfc-editor.org/rfc/rfc9457.html#section-3.1)・[§4.2.1](https://www.rfc-editor.org/rfc/rfc9457.html#section-4.2.1)

修理依頼サンプルの `422` は、入力のどこを確かめればよいかを `detail` の文章で伝えます。画面が該当する入力欄の横に理由を表示したいなら、入力エラー用の `type` を定め、本文に `"errors":[{"pointer":"#/title","detail":"件名を入力してください"}]` を加える設計もできます。`errors` はこの設計で加えた項目です。画面は `pointer` で件名欄を選び、`detail` を人に見せるので、案内文を書き換えても正しい欄に表示できます。[RFC 9457 §3 検証エラーの例](https://www.rfc-editor.org/rfc/rfc9457.html#section-3)・[§3.1.4 detail](https://www.rfc-editor.org/rfc/rfc9457.html#section-3.1.4)

## 変更の上書きを防ぎたいときは 412 を使う

二人が同じ依頼を編集する業務では、後の更新が先の人の修正を消すことがあります。条件付き更新は、**自分が見た版のままなら保存する**方法です。次は、修理依頼サンプルを拡張する場合の設計例です。

1. サーバーは読み取り時に `ETag: "v3"` を返し、取得した内容の版を知らせます。
2. 利用者は更新の要求に `If-Match: "v3"` を付けます。サーバーは保存時にその版と一致するか確かめます。
3. 先に別の人が変更していれば、サーバーは更新せず `412 Precondition Failed` を返します。利用者は最新の内容を読んでから、自分の修正を反映できます。

時間帯が埋まった予約の `409` は、業務上の状態との競合を示します。`412` は、呼び出し側がヘッダーに指定した条件を満たさない場合です。データベースでも版の一致を条件にして書き込むと、確認と保存の間に起きた変更も検出できます。[RFC 9110 §13.1.1 If-Match](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1)・[§15.5.13 前提条件の不一致](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.13)
