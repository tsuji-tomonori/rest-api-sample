# 第5章　応答を見て、次の行動を決める

要求を送ったあと、利用者は何をしたいでしょうか。作成したデータを開きたい人には、その宛先が必要です。入力を間違えた人には、どこを直せばよいかを伝えます。こうして**応答を受け取ったあとの行動**を先に決めると、ステータスコード、ヘッダー、本文の役割が見えてきます。

## 成功した範囲を伝える

HTTP のステータスコードは3桁の数字です。先頭が `2` のコードは成功を表しますが、依頼した仕事がどこまで済んだかはそれぞれ違います。[RFC 9110 §15.3 成功応答](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3)

| 応答する時点で言えること | コード | 呼び出した側に渡すもの |
| --- | --- | --- |
| 要求に成功し、結果を伝えられる | `200 OK` | 検索なら一覧、更新なら変更後の内容など、その操作の結果 |
| 新しいリソースを作成した | `201 Created` | サーバーが宛先を決めた場合は `Location` にその宛先。受付番号などを本文で伝えることもできる |
| 処理を受け付けた。実行の結果はこれから決まる | `202 Accepted` | 現時点の状態と、進み具合や最終結果を確認する手段 |
| 要求を完了し、返す本文がない | `204 No Content` | ステータスと必要なヘッダー。クライアントは本文を読み込まずに次に進む |

たとえば、帳票の生成を後で実行するなら、受付には `202` を使えます。利用者が追跡できるよう、進捗を読む宛先を返します。一方、修理依頼の**登録**は、実際の修理が後日でも、台帳に依頼ができた時点で完了です。サンプルは `201` と `Location: /repair-requests/42` を返すので、受け取った側はその宛先で依頼を開けます。判断するのは、今回の要求で何を引き受けたかです。[RFC 9110 §15.3.2–3](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.2)・[§10.2.2 Location](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.2)

## 失敗したら、何を変えれば先に進めるか

エラーを設計するときは「同じ操作が成功するには、誰が何を変える必要があるか」と考えます。次の表は、よくある原因と応答の対応です。本文の形式も値も正しいのに、直前に別の予約が入って失敗した場合は、入力欄に「形式エラー」と出すと利用者が迷います。[RFC 9110 §15.5 クライアント側のエラー](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5)・[§15.6 サーバー側のエラー](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6)

| 原因を確かめる問い | 典型的な応答と、次の行動 |
| --- | --- |
| 要求を読み取れたか | JSON の構文が壊れていれば `400`。その操作が受け付けない形式なら `415`。送信側で書き方や形式を直す |
| 値が条件に合うか | 形式は正しくても終了時刻が開始より前なら `422`。利用者が値を直す |
| 対象が存在し、その操作ができる状態か | 指定した対象が見つからなければ `404`。予約枠がすでに埋まっていれば `409`。宛先や最新の空きを確かめる |
| 有効な認証情報や権限があるか | `401` では `WWW-Authenticate` で求める認証方式を知らせる。本人を確認できても操作を許さない場合は `403` が候補 |
| 時間を置けば再試行できるか | 要求の頻度が上限を超えたら `429`、サーバーが一時的に利用できなければ `503`。`Retry-After` があれば待ち時間の目安にする |

`429` と `503` は、どちらも「ただちに同じ要求を送り直す」という指示ではありません。再送してよい操作かは、第4章で確認した性質と契約から判断します。[RFC 6585 §4](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)・[RFC 9110 §15.6.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6.4)

修理依頼で確かめると、未登録の番号を指定した照会は `404`、未完了の依頼を探して0件だった場合は `200` と `{"items":[],"next_after":null}` です。後者の検索は成功しています。画面は「未完了の依頼はありません」と案内できます。

### 機械が読む種類と、人が読む説明を用意する

同じ `404` でも、どの操作で何が見つからなかったのかを知ると対処しやすくなります。**Problem Details** は、こうした説明を共通の形で返すための仕様です。サンプルで存在しない依頼を開くと、次のような応答が返ります。ヘッダーは抜粋です。[RFC 9457 §3](https://www.rfc-editor.org/rfc/rfc9457.html#section-3)

```http
HTTP/1.1 404 Not Found
Content-Type: application/problem+json

{"type":"about:blank","title":"Not Found","status":404,"detail":"修理依頼が見つかりません。"}
```

`type` は問題の種類を示す識別子です。この例の `about:blank` は、HTTP ステータスが示す分類をそのまま使うという意味です。`title` は種類の短い名前、`detail` は今回の状況を人に伝える説明です。プログラムは実際の HTTP ステータスを使って分岐し、問題をさらに区別したいときは `type` を読みます。日本語の説明を推敲しても、分岐の条件は変わりません。[RFC 9457 §3.1](https://www.rfc-editor.org/rfc/rfc9457.html#section-3.1)・[§4.2.1](https://www.rfc-editor.org/rfc/rfc9457.html#section-4.2.1)

アプリの手前にある API Gateway が権限を確かめて応答することもあります。そうした場合に備え、呼び出し側はステータスと `Content-Type` を確かめてから本文を読みます。[AWS「HTTP API の IAM 認可」](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-access-control-iam.html)

## 読んだ時点から変わっていたらどうするか

応答には、あとで内容を再利用できる条件も書けます。たとえば、ブラウザーなどが応答を保存して再利用する仕組みをキャッシュといいます。キャッシュへの保存を禁じたいときは `Cache-Control: no-store` を指定します。修理依頼サンプルは社内の台帳を扱うため、この方針を選んでいます。[RFC 9111 §5.2.2.5 no-store](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.5)

最新の内容を読み込んでも、利用者が編集している間に別の人が保存することはあります。上書きを防ぎたい API では、サンプルを拡張する設計として、次のような**条件付き更新**を選べます。

1. 読み取り時に `ETag: "v3"` を返します。これは取得した内容の版を識別する目印です。
2. 更新する側は `If-Match: "v3"` を添えます。「表示した版と一致するときだけ、この変更を適用する」という条件です。
3. 先に別の人が更新していれば、サーバーは変更を適用せず `412 Precondition Failed` を返します。利用者は最新の内容を読み直し、自分の編集をどう反映するか決められます。

実装時には、データベースでも版の一致を条件にして書き込みます。版を確認してから保存するまでの間に変更が割り込むのを防ぐためです。予約の重なりのような業務上の競合には `409`、要求に明示した前提条件が満たされないときには `412` と分けると、呼び出し側は次の行動を選びやすくなります。[RFC 9110 §13.1.1 If-Match](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1)・[§15.5.13](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.13)
