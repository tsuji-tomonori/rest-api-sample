# 第5章　HTTP ステータスコードから次の行動を決める

社員が「登録」を押したあと、画面はいつ受付番号を表示してよいでしょうか。依頼を保存できたら番号を表示し、件名が空欄なら入力欄に戻します。この分かれ道を画面の担当者に伝えるのが、3桁の **HTTP ステータスコード** とレスポンスの内容です。

## まず成功、入力などの条件、サーバーの問題に分ける

| 分類 | 何が起きたか | 呼び出し側の次の行動 |
| --- | --- | --- |
| **2xx　成功** | リクエストが成功した。どこまで完了したかは各コードで伝える | 登録結果や一覧を表示する |
| **4xx　リクエストに関する問題** | 入力、権限、対象の状態などに、処理を妨げる条件がある | 入力を直す、権限や現在の状態を確かめるなど、個々のコードに応じて対処する |
| **5xx　サーバー側の問題** | サーバーや中継先で処理を完了できなかった | 発生時刻と操作を控える。提供側は同じ時刻のログを調べる |

たとえば、どんな結果にも `200 OK` を返し、本文の `"success": false` だけで失敗を知らせるとどうなるでしょうか。HTTP のステータスで分岐する画面や監視ツールは、その失敗を成功として扱います。登録できたときには `201`、空白だけの件名で登録を断ったときには `422` を返せば、画面は本文の説明を読んで次の行動を案内できます。

## 登録し、開き、削除する

**サンプルで試せる**

| 修理依頼の操作 | ステータスとレスポンス | 画面での扱い |
| --- | --- | --- |
| 件名と場所を送って登録した | `201 Created`。本文に依頼の内容、`Location` ヘッダーに `/repair-requests/42` などの宛先 | 受付番号を表示し、返された宛先で詳細を開く |
| 番号で依頼を開いた、または状態を更新した | `200 OK` と、その依頼の現在の内容 | 件名や状態を表示する |
| 未完了の依頼を検索して0件だった | `200 OK` と `{"items":[],"next_after":null}` | 「未完了の依頼はありません」と表示する |
| あるはずの番号で開いたが登録がない | `404 Not Found` とエラー本文 | 番号を確かめるか一覧に戻る |
| 誤って登録した依頼を削除した | `204 No Content`。本文は空 | JSON の読み取りを省き、一覧を更新する |

修理予定が来週でも、社員が API に頼んだのは「依頼を台帳に登録すること」です。保存が済んだ時点で `201` を返せます。同じように、一覧取得の成功条件は「条件に合う依頼を探せたこと」なので、結果が0件でも `200` です。

## 入力に問題があるときは、直せる形で伝える

**サンプルで試せる**

| 何を送ったか | ステータス | 何を直すか |
| --- | --- | --- |
| JSON の閉じ括弧が欠けている | `400 Bad Request` | JSON の書き方を直す |
| JSON を受け付ける登録先に CSV を送った | `415 Unsupported Media Type` | 本文を JSON に変え、`Content-Type: application/json` を付ける |
| JSON として読めるが、件名が空白だけ | `422 Unprocessable Content` | 件名を入力し直す |

ステータスが結果の種類を、本文が今回の事情を伝えます。**Problem Details** はエラーを共通の形で表す仕様です。存在しない番号を開くと、アプリは次のように返します。ヘッダーは抜粋です。

```http
HTTP/1.1 404 Not Found
Content-Type: application/problem+json

{"type":"about:blank","title":"Not Found","status":404,"detail":"修理依頼が見つかりません。"}
```

画面は実際の HTTP ステータスを見て動作を選び、人には `detail` を表示します。同じコードの問題を区別したいときに使うのが、種類を示す `type` です。`about:blank` は HTTP ステータスが表す分類をそのまま使うという指定です。アプリより手前でエラーが起きると本文の形式が変わる場合があるので、画面は `Content-Type` を確かめて本文を読みます。

## 仕様書を読むときの補足

<details>
<summary>認証、権限、業務上の競合、利用回数の制限</summary>

**設計例（未実装）**　次は HTTP API 一般の例です。認証を AWS に任せた場合、実際のレスポンスは利用するサービスの仕様にも従います。

| ステータス | 選ぶ場面 | 利用者や提供側の対応 |
| --- | --- | --- |
| `401 Unauthorized` | 必要な認証情報がない、または期限切れ | 提供側は `WWW-Authenticate` に認証方式を示す。利用者は有効な認証情報を用意する |
| `403 Forbidden` | 閲覧専用の人が削除を頼んだなど、リクエストを理解したが実行を拒む | 必要な権限を確認する。対象の存在を伏せる設計では `404` も選べる |
| `405 Method Not Allowed` | 指定したメソッドをその宛先が受け付けない | 提供側は使えるメソッドを `Allow` で知らせる。呼び出し側はパスとメソッドを確かめる |
| `409 Conflict` | 請求済みの修理を未完了に戻そうとしたなど、現在の状態と競合する | 最新の状態を確認する。正しく入力した人にも起こり得る |
| `429 Too Many Requests` | 短時間の呼び出しが利用上限を超えた | 呼び出す頻度を下げる。`Retry-After` があれば、次に試す時期の目安にする |

入力欄ごとにエラーを表示する設計なら、Problem Details に `"errors":[{"pointer":"#/title","detail":"件名を入力してください"}]` のような項目を追加できます。画面は `pointer` で対象の欄を選べるので、利用者への案内文を変更しても判定に影響しません。

</details>

<details>
<summary>途中経過、非同期の受付、転送、キャッシュ、上書きの防止</summary>

**設計例（未実装）**　1xx は処理途中の通知です。たとえば `100 Continue` を受けた場合は本文を送信し、最終レスポンスを待ちます。3xx は転送や保存済みの内容の再利用などを伝えます。

- **時間のかかる受付**　月次の修理報告書を後で作るなら、`202 Accepted` で受付までを知らせ、進捗を確認する宛先を案内します。
- **キャッシュの再確認**　保存を許したデータの取得時に `ETag: "v3"` を返し、次の取得で `If-None-Match: "v3"` を受けます。同じ版なら `304 Not Modified` と本文なし、変わっていれば `200` と新しい本文を返します。個人用キャッシュに保存し、毎回再確認する設定は `Cache-Control: private, no-cache` です。実際の修理依頼サンプルは `no-store` を返し、保存を禁じています。
- **他の人の更新を守る**　更新時に `If-Match: "v3"` を送り、サーバーでもその版に一致する行だけを更新します。先に別の人が保存していれば、`412 Precondition Failed` を返します。利用者は最新の内容を読んでから修正できます。

</details>

<details>
<summary>500、502、503、504 で調べる場所と再送の判断</summary>

**設計例（未実装）**　呼び出し側は発生時刻と操作を記録し、提供側は次の違いから調査を始めます。

| ステータス | 何が起きたか | 調査の手掛かり |
| --- | --- | --- |
| `500 Internal Server Error` | アプリ内部の予期しない例外などで処理できなかった | アプリのログと処理箇所 |
| `502 Bad Gateway` | 中継サーバーが、接続先から不正なレスポンスを受け取った | 中継先が返した形式とそのログ |
| `503 Service Unavailable` | 過負荷や保守で一時的にサービスを提供できない | 負荷と復旧の見込み。次に試せる時期を示せるなら `Retry-After` を返す |
| `504 Gateway Timeout` | 中継サーバーが、接続先から期限内にレスポンスを受け取れなかった | 接続先の処理時間と中継の待ち時間 |

`Retry-After: 60` は待ち時間の目安が60秒という意味です。実際に再送する前に、同じ操作を繰り返したときの効果を確認します。修理依頼の登録では、すでに保存されていても返事を受け取れず、もう一度送ると2件になる場合があります。

</details>

## この章で決めたこと

- 成功したときは、登録なら 201、照会なら 200、本文を返さない削除なら 204 を返す。
- 検索結果が0件なら空の一覧、指定した1件が見つからなければ 404 を返す。
- 操作ごとに、ステータス、必要なヘッダーと本文、利用者の次の行動を対応付ける。この組を設計シートの成功・失敗の欄に書く。
