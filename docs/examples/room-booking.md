# 実例編 補足　会議室予約に同じシートを使う

修理依頼では、同じ部屋から同じ件名が届いても2件として受け付けました。会議室では、同じ部屋を同じ時間に使えるのは一組だけです。この要件が入力、権限、競合、再送の四つの判断をどう変えるか、修理依頼と同じ欄に記入します。ここで扱うのは設計例です。[修理依頼の記入例](06-contract.md) ｜ [空欄の設計シート](../templates/contract-sheet.md)

## A　API 全体で決めること

| 欄 | 選んだものと理由 |
| --- | --- |
| A1 利用者の行動 | 社員が部屋ごとの予定を調べ、空いている時間を予約する。後で本人が取り消せる |
| A2 リソースと宛先 | 部屋を選んで申し込むため、登録先は `/rooms/{room_id}/reservations`。確定後は予約番号だけで特定できるので、個別の宛先は `/reservations/{reservation_id}` |
| A3 共通の決まり | 時刻は UTC との時差付き。日別の予定表は日本時間の午前0時から翌日午前0時までに重なる予約を返す。隣り合う予約は認める。社員は部屋の予定を読める |

## B　操作ごとに決めること

| 操作の欄 | 会議室を予約する場合 |
| --- | --- |
| B1 目的 | 社員が1室の利用時間を確保し、予約番号を受け取る |
| B2 メソッドとパス | `POST /rooms/3/reservations`。利用する部屋は3番、予約番号はサーバーが採番する |
| B3 入力の置き場所 | 部屋番号はパス、開始・終了時刻は JSON 本文。申込みごとに決めた操作キーを `Idempotency-Key` ヘッダーで送る |
| B4 入力の条件 | 開始と終了は両方必須。終了は開始より後。同じ部屋では時間帯が重なる2件を確定させない |
| B5 権限 | 予約者は認証済みの社員から記録する。同僚も予定は読めるが、取り消せるのは予約者本人 |
| B6 成功時 | `201` と予約番号・部屋・開始・終了。`Location` に `/reservations/48` などの宛先 |
| B7 失敗時 | 終了が開始以前なら `422` で入力を直す。他の人が先に確保していたら `409` で予定表を開き直す |
| B8 再送・途中失敗 | 同じ社員・キー・内容なら24時間以内は最初の予約番号を返す。予約とキーは一緒に確定する。同じキーで内容が違えば `409` |
| B9 完成を確かめる例 | 10時〜11時に予約がある場合、10時30分〜11時30分は `409`、11時〜12時は `201`。別々の申込みが同時に同じ枠を選んでも成立は1件 |

たとえば6月12日の10時から11時までなら、次の本文を送ります。

```json
{"starts_at":"2030-06-12T10:00:00+09:00","ends_at":"2030-06-12T11:00:00+09:00"}
```

## C　公開前に確かめること

- **C1 結果を予測する。** 画面で空きを見てから申し込むまでの間に、他の人が予約することがあります。確定時に DB 側で部屋と時間の重なりを検査します。保存前に失敗したら予約もキーも残らず、保存後に返事が途切れたら同じキーで結果を取り出せます。
- **C2 OpenAPI に転記する。** 部屋番号とキーを `parameters`、開始と終了を `requestBody` に書きます。`responses` には `201` の取得先のほか、`409` の時間帯重複と `422` の入力誤りを、画面が取る行動と一緒に記録します。
- **C3 公開済みの契約を変える。** 初回公開です。将来キーを任意から必須にすると、旧画面の送信は通らなくなります。公開前にキーの要否と有効期間を合意します。

<details>
<summary>条件が変わったら　一括予約と通知の途中失敗</summary>

一つの研修に午前と午後の枠が両方必要なら、午後が取れなかった時点で午前も確定を取り消します。別々の会議100件を取り込む業務なら、成功した99件を残し、失敗した行と理由を返す方法が選べます。

予約の後にメールを送る場合は、予約と「通知待ち」の記録を同時に保存します。メール送信が失敗しても部屋は確保済みです。通知だけを再開し、重ねて届ける可能性があれば通知 ID で照合します。

</details>

時刻・競合・再送の根拠は [RFC 3339 §5.6](https://www.rfc-editor.org/rfc/rfc3339.html#section-5.6)、[PostgreSQL の予約重複制約](https://www.postgresql.org/docs/current/rangetypes.html#RANGETYPES-CONSTRAINT)、[AWS の再送設計](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)を参照してください。
