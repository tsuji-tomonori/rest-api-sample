# 実例編 06　修理依頼の登録を1枚にまとめる

[教科書 06　操作の契約](../textbook/06-contract.md) ｜ [設計シート B1〜B9　操作ごとの決定](../templates/contract-sheet.md#operation)

## 要望と決めること

同じ部屋の椅子について、二人の社員がそれぞれ修理を頼むことがあります。件名と場所が同じでも、別の不具合かもしれません。そこで、届いた依頼を一件ずつ登録します。この決定には、返事を受け取れなかった画面が自動で送り直すと、同じ依頼が2件になり得るという面もあります。

## 選択肢と選んだ理由

**A1 利用者の行動**には、社員が「依頼する」「後で状況を開く」、総務が「未完了を探す」「完了にする」「誤登録を取り除く」と書きます。**A2 リソースと宛先**は修理依頼1件とその集合です。**A3 共通の決まり**として、参加者は同じ台帳を使い、一覧は受付番号順に最大100件ずつ返します。次のページでは返された `next_after` を `after` に渡します。

この五つの行動のうち、まず「依頼する」だけを操作欄に記入します。全員が変更できる共有台帳を選んだので、登録する社員に依頼者 ID を入力させる欄はありません。

## 条件が変わったら

依頼者本人だけが変更できる業務なら、B5 に「登録時に認証済みの利用者を記録し、変更時に保存済みの依頼者と照合する」と追記します。B9 にも「同僚が変更すると拒否され、元の状態が残る」を加えます。こうすると、権限を決めた結果がテスト項目に反映されます。申込みの再送を安全にしたい場合は、[会議室予約の記入例](room-booking.md)で B8 の違いを比べられます。

## 設計シートの記入結果

| 操作の欄 | 修理依頼を登録する場合 |
| --- | --- |
| B1 目的 | 社員が修理を頼み、受付番号で同じ依頼を後から開く |
| B2 メソッドとパス | `POST /repair-requests`。サーバーが受付番号を付ける |
| B3 入力の置き場所 | `Content-Type: application/json`。本文は `{"title":"椅子がぐらつく","location":"第2会議室"}` |
| B4 入力の条件 | 両方必須。前後の空白を除いた長さは各1〜100文字。ヌル文字や、`id` など未定義の項目を含めると入力エラー |
| B5 権限 | 台帳の利用を許可された人が全員の依頼を扱う。AWS では入口で呼び出し権限を確認する。手元のサンプルは認証を省く |
| B6 成功時 | `201`。本文に受付番号、件名、場所、初期状態 `open`。ヘッダーの `Location` は個別の依頼のパス |
| B7 失敗時 | JSON の構文なら `400`、本文の形式なら `415`、件名や場所の条件なら `422`。画面は理由を表示し、入力を直せるようにする |
| B8 再送・途中失敗 | 保存後に返事が途切れると、同じ本文の再送でもう1件できる。画面は自動再送を控え、利用者に結果が不明であることを知らせる |
| B9 完成を確かめる例 | 登録後の `Location` に `GET` すると `200` と送った件名・場所・状態 `open` が返る。空白だけの件名なら `422` で件数は増えない |

**C1 結果を予測する**では、別の担当者にこの表を渡します。「件名の前後に空白がある場合」「件名が空白だけの場合」のそれぞれについて、保存される値とレスポンスを答え合わせできます。[空欄の設計シート](../templates/contract-sheet.md)
