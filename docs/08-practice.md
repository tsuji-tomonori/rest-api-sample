# 第8章　会議室の予約なら、何が変わるか

**設計例（未実装）**

修理依頼では、同じ部屋の椅子について2件を受け付けることがあります。会議室を予約する場合は、同じ部屋を同じ時間帯に確保できるのは一人だけです。[修理依頼に使った設計シート](06-contract.md)にこの条件を加えると、成功するタイミング、失敗の知らせ方、再送の扱いがどう変わるでしょうか。

## 会議室を予約する操作の設計シート

| 設計の質問 | 会議室を予約する場合 |
| --- | --- |
| 誰が何をしたいか | 社員が空いている会議室を押さえ、あとで予約番号を使って確認・取り消しできる |
| 何を1件とし、どのメソッドとパスを使うか | 1件は1室の時間枠。`POST /rooms/3/reservations` で3番の部屋に予約を作り、サーバーが予約番号を付ける |
| 何をどこに送るか | 部屋の番号はパス、開始・終了は JSON 本文。`Content-Type: application/json` を付ける。再送に備えて申込みごとの操作キーをヘッダーに送る |
| 誰がどのデータを扱えるか | 社員は部屋ごとの予約時刻を閲覧でき、取り消せるのは予約者本人。予約者はサーバーが認証済みの社員から決める |
| 入力の条件は何か | 開始・終了は時差を含む日時で、ともに必須。終了は開始より後。同じ部屋では利用時間の重なりを認めない |
| 成功時に何を返すか | `201` と予約番号・部屋・開始・終了時刻。`Location` には、新しい予約の `/reservations/48` のようなパスを返す |
| 失敗時にどう直せるか | 終了が開始以前なら `422` で入力を直す。既存予約と重なれば `409` で予定表を読み直し、空いている時間を選ぶ |
| 再送時はどうなるか | 同じ社員・操作キー・申込内容なら、同じ予約番号を返す。この設計ではキーの有効期間を24時間とし、期限を過ぎたら予約状況を確認する |
| 何を確認すれば完成か | 10時〜11時の予約があるとき、10時30分開始は `409`、11時開始は `201`。二人が同時に同じ時間枠に申し込んでも予約は1件 |

## 予約に必要な時刻をどう表すか

たとえば3番の部屋を日本時間の6月12日10時から1時間使う場合、登録のリクエストには次の本文を付けます。

```json
{"starts_at":"2030-06-12T10:00:00+09:00","ends_at":"2030-06-12T11:00:00+09:00"}
```

部屋と日付から予定を探す画面は、`GET /rooms/3/reservations?date=2030-06-12` を使います。この設計での「1日」は日本時間の午前0時から翌日の午前0時までです。その日に少しでも重なる予約を `200` と一覧で返し、予約がなければ空の一覧を返します。予約者が取り消す場合は `DELETE /reservations/48` を受け、取り消しが済んだら `204` を返します。社内の共有台帳である修理依頼と、本人の予約だけを取り消せるこの例とで、利用者に許す操作が違います。

予約の終了は、次の人が使い始められる時刻とします。10時〜11時の予約があるとき、10時30分〜11時30分は重なり、11時〜12時は隣り合います。二人の画面が同時に「空き」を表示しても、確定時に重なりを検査すれば、一方に `201`、もう一方に `409` を返せます。PostgreSQL なら、部屋が同じで時間帯が重なる行を保存できない制約を使えます。

## 保存前の失敗と、保存後の通信切れを分ける

画面は新しい申込みごとに操作キーを作ります。この例では、`Idempotency-Key: booking-8f31` のようなヘッダーで送り、同じ申込みの再送には同じキーと本文を使います。サーバーは「社員とキー」の組を一意にして、申込内容と予約番号を予約そのものと一緒に保存します。複数の変更を一緒に確定する仕組みを**トランザクション**と呼びます。

| どこで止まったか | 残ったデータ | 同じ申込みを再送した場合 |
| --- | --- | --- |
| 確定（コミット）前に保存に失敗し、取り消した | 今回の変更はすべて元に戻る（ロールバック） | 空きを調べ直し、最初から処理する |
| 確定後にレスポンスが途切れた | 予約番号と操作キーが残る | 保存済みの番号を返し、予約は増えない |

同じキーのリクエストが同時に届いた場合も、確定するのは1件です。もう一方には確定した予約番号を返します。有効期間内に同じキーで時間帯だけ変えた場合は `409` とし、別の申込みには新しいキーを使ってもらいます。修理依頼サンプルの登録に、この重複を防ぐ機能はありません。

<details>
<summary>発展　確定済みの予約を保ち、通知だけを再開する</summary>

予約の確定後に外部サービスから通知するなら、予約と同じトランザクションで「未送信」の記録も残します。通知に失敗しても部屋は確保済みなので、通知の工程だけを再開します。通知先が受理した直後に通信が途切れる場合に備え、同じ通知 ID を使って再送し、受け取る側でも処理済みの ID を照合します。この方法を**トランザクショナル・アウトボックス**と呼びます。

「外部手配が成功した時点で予約成立」という別の要件なら、部屋を仮押さえし、手配が最終的に失敗したときに解除します。確定済みの操作の効果を別の操作で打ち消すのが**補償**です。処理が長ければ `202 Accepted` で受付を知らせ、この例では `Location: /operations/81` を返します。画面は `GET /operations/81` で進捗を確認でき、同じ受付を再送した場合にも同じ処理 ID が返ります。

</details>

<details>
<summary>発展　一括予約のうち1件が失敗した場合</summary>

研修に午前と午後の両方の部屋が必要なら、2件を一つのトランザクションで確定します。午後の部屋が埋まっていれば、今回の申込みで取れる部屋は0件です。一方、総務が別々の会議を100件取り込む場合は、99件の成功を残し、失敗した行に理由を付けて返すほうが手間を減らせます。判断の基準は「途中までの成功を、そのまま利用できるか」です。

</details>

## この章で決めたこと

- 予約を保存するときに時間帯の重なりを判定する。同時に申し込んだ2人にも、一方は確定を示す `201`、もう一方は競合を示す `409` を返す。
- 再送を受け付けるなら、同じ申し込みを識別する方法を決める。
- 予約と通知のどこまでを一緒に確定し、失敗したらどこから再開するかを決める。
