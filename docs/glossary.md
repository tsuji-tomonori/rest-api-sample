# 用語集

修理依頼を1件登録する場面を使って、本文に出てくる言葉を整理します。

## 何を指すか

| 用語 | この教材での意味 | 修理依頼の例 |
| --- | --- | --- |
| API / Web API | プログラムから機能を使う取り決め。ここではネットワーク越しに HTTP で呼び出す Web API を扱う | 画面から件名と場所を送り、受付番号を受け取る |
| REST | 対象を識別し、その状態を表すデータを共通の操作でやり取りする設計様式 | 同じ受付番号で、依頼を読んだり状態を変更したりできる |
| リソース / 表現 | リソースは API が扱う対象。表現は、その時点の対象を伝えるデータ | 対象は42番の修理依頼。件名や状態を入れた JSON がその表現 |
| URI / URL | URI は対象を識別する名前。URL は、場所とアクセス方法を示す種類の URI | `https://example.com/repair-requests/42` はどちらにも当てはまる |
| パス / パスパラメータ | パスは URL のうち対象への道筋を表す部分。波かっこは仕様書で値を入れる位置を示す | `/repair-requests/{request_id}` の `{request_id}` を実際の受付番号に置き換える |
| クエリパラメータ | `?` の後で渡す条件。パスと組み合わせて読みたい結果を指定する | `?status=open` なら未完了の依頼に絞る |

## HTTP で何を渡すか

| 用語 | この教材での意味 | 修理依頼の例 |
| --- | --- | --- |
| クライアント / サーバー | 呼び出す側と、処理して結果を返す側 | 画面が受付 API を呼ぶ |
| リクエスト（要求）/ レスポンス（応答） | クライアントが送るメッセージと、サーバーから返るメッセージ | 「この依頼を登録してほしい」と「42番で登録した」 |
| メソッド | 対象に求める操作を表す HTTP の語 | `GET` は取得、`POST` はこの例では登録 |
| ヘッダー / ボディ（本文） | ヘッダーは形式などを示す追加情報。ボディには渡すデータが入る | `Content-Type: application/json` が本文の読み方を示し、本文に件名と場所が入る |
| JSON | データを書く形式。`{}` は名前と値を組にしたオブジェクト、`[]` は順序のある配列 | `{"status":"open"}` は「状態が未完了」を表す |
| ステータスコード | リクエストの結果を示す3桁の数字 | `201` なら新しい依頼を作成した |
| 冪等（べきとう） | 同じリクエストを複数回送っても、サーバーに意図した効果が1回分と同じ | 同じ依頼を2回削除しても、台帳から消えるのは1件 |
| 認証 / 認可 | 認証は呼び出し元を確かめること。認可は、その人やプログラムが対象に対して何をできるかを判断すること | 社員を特定した上で、その依頼を変更できるか判定する |

## 設計を何に残すか

| 用語 | この教材での使い分け |
| --- | --- |
| 契約 | 入力、成功時の結果、失敗の伝え方など、API の提供側と利用側が守る取り決め |
| 設計シート | 操作ごとに、誰が何を送り、何が返り、どう確かめるかを人が決めて書く表 |
| OpenAPI 仕様書 | パス・メソッド・入力・レスポンスなどをプログラムでも読める形で記録した文書 |
| YAML（ヤムル） | 設定などを書くデータ形式。この教材では字下げで項目の入れ子を表し、OpenAPI 仕様書を書く |
| スキーマ | データの形や許す値の規則。たとえば受付番号は1以上の整数と定める |
| Swagger UI | OpenAPI 仕様書を読み込み、ブラウザーから入力例や操作を確認できる画面 |
