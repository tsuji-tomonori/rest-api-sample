# 第2章　REST とリソース

社員が「椅子がぐらつく」と届け出ました。修理が終わると、総務はその依頼を完了にし、社員は受付時と同じ番号で結果を確かめます。状態は変わっても、追いかけているのは同じ依頼です。

**REST（Representational State Transfer）** は、Web のように複数のプログラムが通信するシステムの設計様式です。設計の出発点は「利用者が後からもう一度指し示したいものは何か」です。REST では、その対象を**リソース**と呼びます。今回なら、修理依頼1件も、総務が毎朝開く未完了の依頼一覧もリソースになります。

## 同じ宛先で、変わった状態を読む

**サンプルで試せる**

受付番号が `42` なら、社員は `GET /repair-requests/42` で依頼を読めます。`GET` は読み取りを求める HTTP の操作名です。`/repair-requests/42` はその依頼を指す宛先のパスです。実際に試すときは、登録時に返った番号を使います。

登録直後の JSON を読むと、件名と場所に加えて、サーバーが付けた受付番号 `id` と状態 `status` が分かります。

```json
{"id":42,"title":"椅子がぐらつく","location":"第2会議室","status":"open"}
```

総務が同じパスに `PATCH` で `{"status":"completed"}` を送ると、受付番号、件名、場所を保ったまま状態が「完了」に変わります。社員がもう一度同じ宛先を読むと、`status` は `completed` です。

ここで依頼を指し示すのが**識別子**、レスポンスの JSON のように、その時点の状態を伝えるデータが**表現**です。HTTP では対象を **URI**（リソースを識別する文字列）で指します。画面と API が宛先と表現の意味を共有していれば、どのテーブルに依頼を保存したかを画面側が知る必要はありません。

## なぜ共通の操作で扱うのか

画面のボタンごとに「社員用に依頼を表示」「総務用に依頼を表示」という API を作ると、同じ依頼を読む方法が画面ごとに増えます。このサンプルでは、どちらも同じ宛先に `GET` を送ります。対象は宛先で、求める操作はメソッドで伝えます。成功時の `Content-Type: application/json` からは、受け取った本文の形式も分かります。

こうして、対象の識別、表現を介した操作、メッセージの読み方をそろえるのが REST の**統一インターフェース**です。

<summary>発展　ハイパーメディアと REST の制約</summary>

提唱者の Roy Fielding はさらに、レスポンス中のリンクなどを手がかりに次の操作を選ぶことを求めています。これを**ハイパーメディア**と呼びます。このサンプルでも、登録後に開く宛先はレスポンスの `Location` で分かります。そこから状態をどう変更するかは、あらかじめ公開した仕様書で確認します。

| 制約 | 修理依頼の仕組みで考えると |
| --- | --- |
| クライアントとサーバーの役割を分ける | 画面は依頼を表示し、サーバーはその記録を管理する。互いに内部の作りを変えやすい |
| 各リクエストに必要な情報を含める（ステートレス） | 照会するたびに受付番号を送るので、サーバーは直前にどの画面を開いたかを覚えずに処理できる。依頼自体の状態は保存する |
| レスポンスを再利用できる条件を明らかにする（キャッシュ） | 保存を許せば同じ内容を取り直す時間を省ける。この教材では社内の依頼を扱うため、アプリが `Cache-Control: no-store` を返す |
| 通信を階層に分ける | AWS では API Gateway が入口でリクエストを受ける。利用者は奥にある関数や DB の接続先を知る必要がない |
| コードを必要に応じて配る（任意） | ブラウザーにスクリプトを渡し、利用者側で実行して機能を広げられる |

</details>

## この章で決めたこと

- 利用者が後から開きたいものをリソースにする。
- 同じ依頼は同じ受付番号で指し、状態が変わったら新しい表現を返す。
- 読む、変更するといった操作には、共通のメソッドを使う。
