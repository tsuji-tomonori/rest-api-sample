# 第2章　REST とリソース

「注文を確定する」「配送先を変える」「進み具合を見る」。操作を一つずつ別の名前で公開することもできますが、三つとも同じ注文を扱っています。この共通点から考えると、利用者は注文の宛先を一度知るだけで、内容を読み、必要な変更を頼めます。

**REST（Representational State Transfer）** は、Web のような分散システムで、独立したプログラムが共通のルールでやり取りするための設計様式です。提唱者 Roy Fielding の原典は、設計にどのような制約を置くと何が得られるかを説明しています。HTTP のメソッドや応答の意味を定める仕様は RFC 9110 です。[Fielding 第5章](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm)・[RFC 9110 §1.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-1.3)

## 何を一つの対象として扱うか

REST で名前を付けて扱う対象を **リソース** と呼びます。境界を決めるときは、**「利用者が後からもう一度指し示したいものは何か」** と考えます。注文1件も、「未発送の注文」のように中身が入れ替わる一覧も、対象になり得ます。[Fielding §5.2.1.1](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm#sec_5_2_1_1)

| 決めること | 注文ならどう考えるか |
| --- | --- |
| 何を独立して扱うか | 注文を一つの対象にする。分割発送を追跡するなら、荷物にも個別の番号を付ける |
| 何が変わっても同じ対象か | 配送先や発送状況が変わっても注文番号は変えない。注文番号から同じ注文を参照できる |
| 相手には何を見せるか | 一覧なら番号と発送状況、詳細なら明細も渡す。画面が必要とする情報を選ぶ |

対象を指す名前が **識別子**、その対象の状態を伝えるデータが **表現** です。たとえば、`/orders/42` が指すのは注文42です。一方、`{"id":42,"status":"shipped"}` は、その注文が発送済みであることを JSON 形式で表しています。保存先の表を分割しても、この宛先と表現についての約束を守れば、利用者は同じように注文を読めます。[RFC 9110 §3.1–3.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-3.1)・[Microsoft Azure Architecture Center のリソース設計指針](https://learn.microsoft.com/en-us/azure/architecture/best-practices/api-design#define-restful-web-api-resource-uris)

## 状態を変えるか、業務の操作を表すか

「注文を取り消す」という同じ要望でも、後で知りたいことによって設計が変わります。取消済みかどうかだけを扱うなら、注文の状態を変える方法があります。取消理由や申請者を記録し、承認結果を問い合わせるなら、「取消申請」を独立した対象にすると、申請1件の経過を追えます。

目的が特定の手続きを呼び出すことなら、操作に名前を付ける方法もあります。こうした設計は RPC（遠隔手続き呼び出し）の発想です。たとえば Google の設計指針は、標準操作で意図を十分に表せない場合に独自の操作を認めています。選ぶ基準は「動詞が使えるか」よりも、**利用者が追跡したい対象や、依頼したい仕事を明確に示せるか**です。[Google AIP-136 Custom methods](https://google.aip.dev/136#guidance)

## REST の制約は何に効くか

注文、予約、請求で対象が変わっても、各要求の読み方を共通にできます。これを支えるのが、REST の中心にある **統一インターフェース** です。対象を識別し、表現を介して操作し、メッセージ自体から意味が分かるようにします。さらに原典では、応答に含まれるリンクなどをたどって次の操作を選びます。たとえば、出荷後の注文に荷物の追跡先が含まれていれば、利用者は宛先の組み立て方を知らなくても先へ進めます。これが **ハイパーメディア** の役割です。仕様書に次の宛先をあらかじめ列挙する設計では、利用者はその記載を頼りに操作します。[Fielding §5.1.5](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm#sec_5_1_5)

| ほかの制約 | 設計上の効果 |
| --- | --- |
| クライアントとサーバーの役割を分ける | 画面とデータ管理を別々に変更しやすくなる |
| 各要求に処理に必要な情報を含める（ステートレス） | 直前の画面操作を知らないサーバーでも応答できる。注文自体の状態はサーバーに保存できる |
| 応答を再利用できる条件を示す（キャッシュ） | 同じ内容を取り直す時間を減らせる。最新の状態が必要なら再利用の条件を厳しくする |
| 通信を階層に分ける | 利用者に示した宛先を保ちながら、手前に中継や認証の仕組みを置ける |
| 実行するコードを必要に応じて配る（任意） | ブラウザーなどにスクリプトを配り、配布後に機能を広げられる |

各制約には代償もあります。たとえば、再利用できる応答は通信を減らせますが、その間に対象の状態が変わることがあります。API の設計では、利用者がどの程度新しい情報を必要とするかまで決めます。[Fielding §5.1.2–5.1.7](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm#sec_5_1_2)・[RFC 9111 §5.2.2](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2)
