# 第4章　操作に合うメソッドを選ぶ

設計シートの B2「メソッドとパス」と B8「再送・途中失敗」を埋めます。メソッドを選ぶ手掛かりは、リクエストの前後で利用者が何を変えたいかと、変更先を誰が決めるかです。

## 定義

**HTTP メソッド**は、宛先のリソースに何を求めるかを示す操作名です。同じ宛先でも、内容を読むときと置き換えるときではメソッドが変わります。

## メソッドの選択肢

| メソッド | 選ぶとき | 典型的なリクエスト |
| --- | --- | --- |
| `GET` | 一覧や1件の現在の内容を読みたい | `GET /books`、`GET /books/42` |
| `POST` | 宛先にデータを渡して処理を頼みたい。作成先をサーバーが決める登録にも使う | `POST /books` に新しい書籍の情報を送る |
| `PUT` | 宛先はすでに分かっていて、そこに置く内容の完成形を指定したい。契約で許せば新規作成もできる | `PUT /profiles/42` にプロフィールの更新可能な項目一式を送る |
| `PATCH` | 特定の部分だけどう変えるかを指定したい | `PATCH /profiles/42` に表示名の変更を送る |
| `DELETE` | その宛先から対象を取り除きたい | `DELETE /books/42` |

## 選ぶ基準

**読むだけなら何を送るか。** `GET` は利用者が状態の変更を求めない**安全なメソッド**です。検索条件は通常クエリに置きます。`GET` と `DELETE` の本文には一般に定められた意味がなく、受信側が拒否することもあります。

**ログインや計算は登録か。** `POST` には入力を処理させる用途もあります。たとえばパスワードによる本人確認とセッションの開始には、HTTPS の `POST /sessions` で本文を送る設計が取れます。保存せずに見積もりを計算して返す操作にも使えます。

**消したあとに何を見せるか。** 通常の宛先ではもう取得できない契約なら、データを物理的に消しても、内部に削除日時を残しても `DELETE` を使えます。引き続き同じ宛先で「取消済み」を見せたいなら、状態を変える操作として設計します。

**返事が途切れたら、同じ操作を繰り返せるか。** 同じリクエストを繰り返しても意図した効果が1回分と同じ性質を**冪等**（べきとう）と呼びます。`GET`、`PUT`、`DELETE` は冪等です。`POST`、`PATCH` の再送が安全かは操作の契約によります。「件数を3に設定」は繰り返しても3ですが、「件数を3増やす」は繰り返すと6増えます。

## よくある誤り

- **削除を `GET` で受け付ける。** リンクの先読みでも状態が変わってしまいます。対象を取り除く意思を `DELETE` で伝えます。
- **一部の入力だけで `PUT` を受け付け、残りを暗黙に保持する。** 利用者が指定するのが部分変更なら `PATCH` を選び、省略した項目と `null` を送った項目の意味を決めます。
- **返事がない登録を自動で送り直す。** 最初の登録は完了し、返事だけが失われた可能性があります。再送を許すなら、同じ依頼を識別するキーなどによる重複防止と、結果を照会する手順を取り決めます。

<details>
<summary>発展　冪等性と、途中で失敗したときの扱い</summary>

冪等性は結果のステータスコードが毎回同じという意味ではありません。削除の1回目が成功、2回目が「対象なし」でも、対象が消えているという効果は同じです。

一方、変更をひとまとまりにして全部適用するか、一つも適用しないかという性質を**原子性**と呼びます。一つの `PATCH` に含まれる変更はまとめて適用する必要があります。複数のリクエストに分けた業務の途中で止まったときに、どこから再開するかは別の契約です。第6章で完成条件と一緒に決めます。
