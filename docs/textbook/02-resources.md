# 第2章　REST とリソース

設計シートの A2「リソースと宛先」を決めます。業務で使う名詞を挙げ、利用者があとで同じものを指定して読みたいか、複数件をまとめて探したいかを考えます。

## 定義

**REST**（Representational State Transfer）は、ネットワーク越しに情報をやり取りするシステムの設計様式です。扱う対象を**リソース**と呼び、対象を指す宛先を決めます。通信で渡すのは、その時点の状態を表すデータです。これを**表現**と呼びます。たとえば書籍はリソースで、書名や著者をまとめた JSON は、その書籍の表現の一つです。

宛先が示すのは対象です。同じ対象を読むときも更新するときも、その対象を指す宛先を使います。何を頼むかは第4章のメソッドで伝えます。

## 対象の切り分け方

| 業務で必要なこと | 対象の決め方 | パスの例 |
| --- | --- | --- |
| 全件から探す、新規に加える | 同じ種類のものを集めた「集合」を一つの対象にする | `/books` |
| 特定の1件を繰り返し開く | 集合の後に、その1件を区別できる値を付ける | `/books/42` |
| 親の中でしか子を特定できない | 親を示してから、子の集合と番号を書く | `/books/42/chapters/3` |
| 現在の値が分かれば足りる | 状態をその対象の項目にする | 書籍の `status` |
| 変更ごとの理由・日時を後で照会する | 記録ごとに宛先を持てる対象にする | `/changes/81` |

## 選ぶ基準

- **何が変わっても同じ1件か。** 名前や状態が変わっても同じ1件を開きたいなら、変わりにくい番号などを識別子に使います。
- **親がなければ子を特定できないか。** 親の中だけで通じる番号なら親も宛先に含めます。単独で通じる番号なら、一覧を見つけた順番や組織図までパスに写す必要はありません。
- **どんな名前なら利用者が同じ意味で読めるか。** 集合に業務上の名詞を付け、同じ概念の綴りをそろえます。複数形・小文字・ハイフンは命名規約として選べます。HTTP が階層の数や名詞の綴りを指定するわけではありません。

## よくある誤り

取得・更新のたびに `/getBook/42`、`/updateBook/42` と名付けると、同じ書籍に操作の数だけ宛先が増えます。まず対象を `/books/42` にまとめ、操作を選びます。業務手続きを独立した対象にするかは、「あとで手続きそのものを照会したいか」で判断します。

REST の原典は Fielding の学位論文です。クライアントとサーバーの役割を分け、各リクエストには処理に必要な情報を含めます（ステートレス）。サーバーがリソースの状態を保存することとは両立します。さらに、応答を再利用できる条件を示し、途中に中継層を置けるようにします。

**統一インターフェース**には、リソースの識別、表現を介した操作、意味を読み取れるメッセージ、応答中のリンクなどから次の操作を選べることが含まれます。利用側へ実行用コードを配ることは任意です。
