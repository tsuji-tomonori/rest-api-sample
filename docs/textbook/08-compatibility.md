# 第8章　互換性とバージョン

設計シートの対応欄　[C3 公開済みの契約を変える](../templates/contract-sheet.md#review)

## 定義

**後方互換性**とは、API を更新したあとも、これまでの利用者が同じ呼び方で同じ仕事を続けられる性質です。新規設計では版の伝え方を、公開済みの API では変更が既存の利用者に与える影響を、設計シートの公開前点検に書きます。

## 選択肢

公開した契約の変更に **セマンティックバージョニング（SemVer）** を採用する場合、番号は `メジャー.マイナー.パッチ` の3つに分かれます。安定版 `1.0.0` からの変更で比べます。

| 何を変えるか | 旧版を使っていた人への影響 | 版の選び方 |
| --- | --- | --- |
| 契約に合うように不具合を修正する | 契約どおりの入力と結果を引き続き使える | パッチを上げて `1.0.1` |
| 任意の検索条件を追加し、省略時の動作を保つ | 利用者は必要になった時点で新機能を選べる | マイナーを上げて `1.1.0` |
| 必須入力を増やす、公開済みの項目を削除・改名する | 以前の入力が拒まれるか、必要な結果を読めなくなる | メジャーを上げて `2.0.0`。移行方法を用意する |

## 選ぶ基準

- **送る側から見る。** 以前は有効だった入力を今も送れるか。省略した値の扱いが変わると、同じ入力で別の結果が返ることがあります。
- **受け取る側から見る。** 型、項目名、ステータス、一覧の順序を使うコードが動くか。返す状態の種類を増やす場合も、既知の状態だけを想定した画面への影響を確かめます。
- **移行する人から見る。** 全員が同時に移行できるなら同じ URL で切り替える方法があります。移行時期を別々に選ぶなら、新旧を識別する入口を用意し、終了日・移行先・旧版の利用終了を確かめる方法を決めます。

変更前に保存したリクエストと期待結果を変更後にも試します。新機能の成功例と、古い使い方が通る例の両方がそろうと、今回維持する範囲を利用者に伝えられます。

## よくある誤り

仕様書の番号を書き換えるだけでは、呼び出し先は変わりません。`openapi` は仕様書を書く規格の版、`info.version` は API の仕様書に付けた版です。利用者に版を選ばせる場合は、その指定方法も公開します。

<details>
<summary>発展　パス、ヘッダー、ステージの使い分け</summary>

パスでメジャー版を選ぶ設計では、たとえば `/v1/items` と `/v2/items` を別の入口にします。互換性を保つ変更は同じメジャー版のパスで配信できます。ヘッダーで選ぶ方式なら、利用可能な値と省略時の版を決めます。

開発環境と本番環境は「どこへ送るか」、契約の版は「何を約束するか」です。API Gateway のステージはデプロイした設定の公開先を示します。環境名やステージ名をパスに載せるかは、契約の版番号とは別に決められます。
