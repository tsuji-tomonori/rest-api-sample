# 第5章　レスポンス

設計シートの対応欄　[B6 成功時・B7 失敗時](../templates/contract-sheet.md#operation)

## 定義

レスポンスは、リクエストを受けたサーバーが結果を知らせるメッセージです。設計シートの「成功時」「失敗時」には、ステータスコード、必要なヘッダー、本文を一組で書きます。

## 選択肢

**2xx は成功、4xx はリクエストの入力・権限・対象の状態などに関する問題、5xx はサーバー側の問題**です。まず「要求した仕事がどこまで済んだか」を決めると、コードを選べます。

| どこまで済んだか | コード | 呼び出し側が受け取るもの |
| --- | --- | --- |
| 取得・更新が済み、結果を渡せる | `200 OK` | 対象の内容や一覧。検索が成功して該当が0件なら空の一覧 |
| 新しい対象を作成した | `201 Created` | 作成先。集合への登録なら `Location` ヘッダーに新しい1件の宛先を示す |
| 処理を受け付け、完了は後になる | `202 Accepted` | 現在の状況と、結果を確かめる方法 |
| 更新・削除が済み、返す本文がない | `204 No Content` | ステータスと必要なヘッダー。本文は空 |

## 選ぶ基準

失敗は「利用者が何を変えれば先へ進めるか」で分けます。同じ失敗には、API 全体で同じコードと本文の形式を使います。

| 何を変えればよいか | コードの候補 | 判断の目安 |
| --- | --- | --- |
| 送る内容・形式を直す | `400`、`415`、`422` | 壊れた JSON は `400`、未対応のメディアタイプは `415`。読めた JSON の値が条件外なら `422` と分ける方針も、値の誤りを `400` にまとめる方針もある |
| 認証情報か操作権限を確かめる | `401`、`403` | 有効な認証情報を求める `401` には `WWW-Authenticate` が必要。操作を拒むときは `403` |
| 指定した対象か操作を確かめる | `404`、`405` | 1件が見つからなければ `404`。対象がそのメソッドを扱わないときは `405` と `Allow` ヘッダーで使えるメソッドを示す |
| 現在の状態を確認してやり直す | `409`、`412` | 業務上の競合は `409`。更新時に `If-Match` で指定した版と一致しなければ `412` |
| 呼び出しの頻度を下げる | `429` | 利用回数が上限に達した。提供側は `Retry-After` で次に試せる時期を知らせられる |

エラー本文には、何が起き、どう直せるかを書きます。共通形式の **Problem Details** を使う場合、メディアタイプは `application/problem+json` です。プログラムは実際の HTTP ステータスと、必要に応じて問題の種類を示す `type` を読みます。人に伝える詳しい事情は `detail` に書けます。

## よくある誤り

入力を拒んだのに `200` とエラー文を返すと、HTTP ステータスを見ている利用者や監視は成功と受け取ります。反対に、検索結果が0件のたびに `404` を返すと、存在する一覧と存在しない宛先を区別できません。成功・失敗は、要求された操作ごとに判断します。

1xx は最終結果に先立つ通知です。3xx には別の宛先への案内や、保存済みの内容を再利用する応答があります。たとえば `ETag` は返した内容の版を示す印です。次の取得で `If-None-Match` を送り、その印が一致すると `304` と本文なしの応答を受け、保存済みの内容を使えます。`Cache-Control: no-cache` は再利用前の確認を求め、`no-store` は保存を禁止します。

5xx のうち `500` は処理中の予期しない失敗、`503` は過負荷や保守などによる一時的な利用不能です。中継するサーバーが接続先から不正な応答を受けたら `502`、応答を期限内に得られなければ `504` です。登録結果が不明なまま再送すると、すでに処理した登録と重複することがあります。
