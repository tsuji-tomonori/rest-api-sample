# 第6章　業務の要望から API を設計する

ここまでに決めた宛先、操作、レスポンスを、社員の仕事に沿って並べます。社員は件名と場所を送り、返された受付番号で後から状況を調べます。この一連の行動を画面と API の担当者が同じように説明できれば、登録に必要なものと、その場で返すべきものが定まります。

## 利用者の行動を並べる

**サンプルで試せる**

まず、社員と総務がすることを一行ずつ書き、対応するリクエストと成功時のレスポンスを置きます。表の `42` は、最初の行でサーバーから受け取った受付番号の例です。

| 利用者の行動 | リクエスト | 成功時のレスポンス |
| --- | --- | --- |
| 依頼を登録する | `POST /repair-requests` に件名と場所を送る | `201` と登録結果。`Location` に新しい依頼のパス |
| 未完了を10件まで探す | `GET /repair-requests?status=open&limit=10` | `200`。本文の `items` に一覧、`next_after` に続きの位置 |
| 42番の状況を確かめる | `GET /repair-requests/42` | `200` と依頼1件 |
| 修理の完了を記録する | `PATCH /repair-requests/42` に `{"status":"completed"}` を送る | `200` と更新後の依頼 |
| 誤って登録した依頼を取り除く | `DELETE /repair-requests/42` | `204`、本文なし。以後、同じ番号を開くと `404` |

## 登録を1枚の設計シートにする

**サンプルで試せる**

次に、操作を一つ選びます。下の表は「新しい依頼を登録する」の記入例です。同じ質問を使うと、画面の担当者と API の担当者が、送る値から失敗時の振る舞いまで同じ順序で確認できます。[空欄の設計シート](templates/contract-sheet.md)

| 設計の質問 | 修理依頼を登録する場合 |
| --- | --- |
| 誰が何をしたいか | 社員が椅子の修理を頼み、受付番号を受け取る。総務はあとで同じ依頼を開く |
| 何を1件とし、どのメソッドとパスを使うか | 1件は一つの修理依頼。`POST /repair-requests` で登録し、サーバーが番号を付ける |
| 何をどこに送るか | `Content-Type: application/json` を付け、本文に `{"title":"椅子がぐらつく","location":"第2会議室"}` を送る。登録時のクエリは使わない |
| 誰がどのデータを扱えるか | 共有台帳を利用できる社員が全員の依頼を扱う。AWS では API Gateway が署名と呼び出し権限を確認する |
| 入力の条件は何か | 件名と場所は両方必須。前後の空白を除いて各1〜100文字とし、ヌル文字を除く。利用者が `id` を送ったら入力エラー |
| 成功時に何を返すか | `201 Created`。本文に受付番号・件名・場所・初期状態 `open`、`Location` に個別のパスを返す |
| 失敗時にどう直せるか | JSON の構文が壊れていれば `400`、未対応の本文形式なら `415`、空白だけの件名なら `422`。理由を読んで該当箇所を直す |
| 再送時はどうなるか | 同じ本文を再送すると別の依頼ができる。レスポンスが途切れたときの自動再送は控える |
| 何を確認すれば完成か | 返された `Location` を `GET` し、入力した件名・場所と初期状態を確かめる。空白だけの件名なら件数は増えない |

シートの最後には、画面から結果を判定できる例を残します。たとえば件名「照明が消える」の前後に空白があれば、それを取り除いて登録します。空白しかなければ `422` で、依頼は増えません。この二つを仕様書の入力例と期待する結果に使えます。

## 件数と再送の扱いを確かめる

**サンプルで試せる**

一覧は番号の小さい順に既定で20件、最大100件まで返します。画面はレスポンスの `next_after` を、そのまま次のリクエストの `after` に渡します。`null` なら最後です。ページをめくる間に依頼が完了すると、未完了一覧から外れます。

同じ番号を2回削除すると、1回目は `204`、2回目は `404` です。依頼を消すという目的は1回目で達成しています。一方、登録のリクエストに返事がない場合は、保存直後に通信が切れた可能性があります。件名と場所が同じ依頼を一覧で見つけても、それだけでは自分の送信結果を断定できません。

**設計例（未実装）**

本人だけが変更できる仕組みを加えるなら、サーバーは認証で確かめた社員と部署を依頼に記録します。API の呼び出し権限を確かめたうえで、個々の依頼を操作してよいかをアプリが判断します。利用者が指定した受付番号や部署名だけで権限を広げることはできません。

たとえば、41番はAさん、43番は同じ部署のBさん、42番は他部署の依頼です。

| Aさんの操作 | 業務要件から決まる結果 |
| --- | --- |
| 一覧を1件ずつ読む | 自部署に絞った後でページを分ける。1ページ目は41番と `next_after: 41`、2ページ目は43番と `next_after: null` |
| Bさんの43番を開き、状態を変更しようとする | 詳細は `200`。変更は `403` で元の状態を保つ。Bさんなら変更できる |
| 他部署の42番を直接指定する | 存在を伏せる方針なら、照会・変更・削除はいずれも `404` |

たとえ本人でも「請求済みの修理は再開できない」と定める業務では、現在の状態との競合を `409` で知らせます。誰が操作できるかと、どの状態なら操作できるかを分けると、必要な確認が見えてきます。

## この章で決めたこと

- 利用者の行動を操作の一覧にし、そのうち一つを選んで設計シートにまとめる。
- 操作ごとに、入力と権限の条件、成功時に返す内容、失敗や再送でデータがどうなるかを決める。
- 登録できる入力と拒む入力、それぞれの結果を添える。第7章ではこのシートを公開仕様書に写す。

## 根拠と参考

- メソッドが伝える操作と、再送時の効果。[RFC 9110 §9](https://www.rfc-editor.org/rfc/rfc9110.html#section-9)・[§9.2.2 冪等性](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)
- 件数が増える一覧のページ分割。[Google AIP-158](https://google.aip.dev/158)
- AWS の呼び出し権限と、アプリで行うデータ単位の認可。[AWS「HTTP API の IAM 認可」](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-access-control-iam.html)・[OWASP「Authorization Cheat Sheet」](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#validate-the-permissions-on-every-request)
- サンプルが許す入力と返す値。[公開仕様書](openapi.yaml)・[入力の型定義](../package/app/schemas.py)
