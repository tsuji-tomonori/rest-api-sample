# 第6章　業務の要望から API を設計する

「修理依頼を登録できるようにしたい」と相談されたら、まず「登録した人は、そのあと何をしますか」と聞いてみましょう。「後日、修理が終わったか確かめたい」という答えなら、受付番号を渡すと依頼を探せます。利用者が次にしたいことから考えると、API が返すべき情報を絞れます。

## 1．利用者の目的から、扱う対象を選ぶ

「誰が、何をして、どうなれば終わりか」を一文で書きます。たとえば「社員が修理を依頼し、受け取った番号で後から対応状況を確認できる」。この一文の「修理依頼」が、登録後も追いかける対象です。番号はサーバーが発行し、件名、場所、現在の状態をその番号に結び付けます。

### 一覧・詳細・登録・変更・削除を並べる

利用者がしたいことを一つずつ、要求と応答の組にします。以下は、修理依頼サンプルで実装した5つの操作です。個別の依頼の例には受付番号 `42` を使います。

| したいこと | メソッドと宛先 | リクエストボディ | 成功するとどうなるか |
| --- | --- | --- | --- |
| 未完了の依頼を最大10件見る | `GET /repair-requests?status=open&limit=10` | なし | `200`。0件なら `items` は空の配列。続きがあれば `next_after` に番号が入る |
| 受付番号42の詳細を見る | `GET /repair-requests/42` | なし | `200` と依頼1件。その番号が存在しなければ `404` |
| 新しく依頼する | `POST /repair-requests` | `{"title":"椅子がぐらつく","location":"第2会議室"}` | `201`。サーバーが採番し、本文に `id`、`Location` ヘッダーにその依頼の宛先を返す |
| 依頼を完了にする | `PATCH /repair-requests/42` | `{"status":"completed"}` | `200` と変更後の依頼。あとから同じ番号で開ける |
| 誤登録した依頼を取り除く | `DELETE /repair-requests/42` | なし | `204` で本文なし。一覧から消え、その番号を再び開くと `404` |

一覧では「どれを何件見るか」をクエリで伝え、詳細では「どの1件か」をパスで伝えます。登録前の依頼にはまだ受付番号がありません。サーバーが番号を付けるこの設計では、クライアントが送るのは件名と場所だけです。親の ID がすでにある場合や、クライアントが新しい ID を決める場合は、[第3章の登録例](03-addresses.md)で比較できます。[RFC 9110 §9 メソッド](https://www.rfc-editor.org/rfc/rfc9110.html#section-9)・[修理依頼の OpenAPI 定義](openapi.json)

## 2．操作を一つ選び、契約を1枚にまとめる

次の表は「修理を依頼する」の記入例です。自分の案件では右の列を書き換え、操作ごとに1枚作ります。入力と応答を並べておくと、たとえば「社員の入力欄に受付番号は要るか」という疑問にも答えられます。

| 決めること | 修理を依頼する場合 |
| --- | --- |
| 誰が何をするか | 利用を許可された社員が、修理してほしい物と場所を届ける |
| 対象とメソッドをどう組み合わせるか | `POST /repair-requests`。番号を発行するのはサーバーなので、登録先には依頼の集合を指定する。登録後は新しい番号で1件を指せる |
| パス・クエリ・ヘッダー・本文のどこに置くか | この登録ではパスに依頼の集合を置き、クエリは使わない。`Content-Type: application/json` は本文の読み方を知らせるヘッダー。件名と場所は保存したい内容なので本文に置く |
| 誰が呼び出し元を確認するか | AWS 上の修理依頼 API では、利用者が要求に署名し、API Gateway が署名と呼び出し権限を確認する。利用者が件名や場所と一緒にパスワードを送る必要はない。[第9章の接続設定](09-aws.md) |
| 入力値をどこまで許すか | 本文の例は `{"title":"椅子がぐらつく","location":"第2会議室"}`。どちらも必須で、前後の空白を除いて1〜100文字 |
| 何をもって成功とするか | 1件を保存し、`201 Created` を返す。`Location` は新しい依頼のパス。本文には `id`、`title`、`location`、初期状態を表す `"status":"open"` が入る |
| 要求を直せば進める場合に何を返すか | JSON の書き方に誤りがあれば `400`、サポート外のメディアタイプなら `415`、空白だけの件名なら `422`。このアプリはそれぞれ `application/problem+json` で理由を返す |
| 応答を受け取れなかったらどうするか | 中継が待ち切れず `504` を返しても、登録が済んでいる可能性がある。件名と場所が同じ別の依頼もあり得るので、一覧だけでは自分の登録の成否を断定できない。このサンプルでは自動再送を控える |
| どうテストするか | 返された `Location` に `GET` すると、登録した件名と場所が返る。件名が空白だけなら、登録件数は増えない |

記入に迷ったら、[何を1件と数えるか](02-rest.md)、[番号や条件をどこに置くか](03-addresses.md)、[どのメソッドで頼むか](04-methods.md)、[利用者に何を返すか](05-responses.md)の順に見直してください。

## 3．実際の使われ方を確かめる

**誰が、どの状態の依頼を変更できますか。** 今回は、利用を許可した社員が共有台帳を操作し、完了した依頼も `open` に戻せます。「本人だけが再開できる」なら、操作する人の権限を確認します。「請求済みの修理は再開できない」なら、権限がある人でも現在の状態を確認します。この設計では、権限が足りない場合は `403`、請求済みのため変更が競合する場合は `409` と区別できます。[RFC 9110 §15.5.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.4)・[§15.5.10](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.10)

**件数が増えたらどう読みますか。** この一覧では番号の小さい順に既定で20件、最大100件ずつ返します。続きがあれば、画面は応答の `next_after` を次の要求の `after` に渡します。`null` なら終わりです。ページをめくる間にも依頼の状態は変わるので、月末時点の全件を集計したい場合には、読んでいる途中で対象が変わらない仕組みを別に決めます。[Google AIP-158「ページ分割」](https://google.aip.dev/158)

**通信が途切れてもやり直せますか。** このサンプルでは、同じ依頼に `DELETE` を2回送ると、1回目は `204`、2回目は `404` です。依頼が消えた状態は変わりません。一方、登録の `POST` を2回送ると同じ本文でも依頼が2件でき得ます。自動再送が必要なら、同じ操作を識別するキーとその有効期間を決めます。途中で止まった処理を取り消す場合と再開する場合は、[第10章の予約と通知の例](10-practice.md)で比べられます。[RFC 9110 §9.2.2 冪等なメソッド](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)・[Amazon Builders’ Library「安全に再試行できる API」](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

**要件を変えたとき、今の利用者はどうなりますか。** たとえば「担当部署」を必須にすると、今の画面からは登録できなくなります。任意の入力として追加し、省略時は従来どおり受け付けるなら、画面を順に更新できます。[Google AIP-180「後方互換性」](https://google.aip.dev/180#adding-components)

待ち時間や処理件数が業務を左右する場合は、「昼休みに何人が送るか」「画面は何秒待てるか」を利用者と決めます。想定する件数と許容する待ち時間を組にして残すと、運用前に同じ条件で測れます。

## 4．別の人が、結果を予測できるか試す

設計メモを画面の担当者に渡し、「件名の前後に空白を入れて送ったら、何が返りますか」「空白だけなら、どこを直しますか」と聞いてみてください。送る要求、返る応答、保存された件数をメモから判断できれば、その例を動作確認に使えます。次の章では、ここで決めた操作を OpenAPI で表します。
