# 第6章　業務の要望から API を設計する

「修理依頼を登録できるようにしたい」と相談されたら、まず「登録した人は、そのあと何をしますか」と聞いてみましょう。「後日、修理が終わったか確かめたい」という答えなら、受付番号を渡すと依頼を探せます。利用者が次にしたいことから考えると、API が返すべき情報を絞れます。

## 1．利用者の目的から、扱う対象を選ぶ

「誰が、何をして、どうなれば終わりか」を一文で書きます。たとえば「社員が修理を依頼し、受け取った番号で後から対応状況を確認できる」。この一文の「修理依頼」が、登録後も追いかける対象です。番号はサーバーが発行し、件名、場所、現在の状態をその番号に結び付けます。

次に、利用者が必要とする操作を並べます。登録先は依頼の集まりを表す `/repair-requests`、照会先は1件を表す `/repair-requests/{request_id}` です。登録には `POST`、照会には `GET` を選べば、社員がしたいことを二つの要求で表せます。総務が「未完了だけを見たい」と言ったら、同じ集まりに絞り込み条件 `?status=open` を加えます。[RFC 9110 §9 メソッド](https://www.rfc-editor.org/rfc/rfc9110.html#section-9)

## 2．操作を一つ選び、契約を1枚にまとめる

次の表は「修理を依頼する」の記入例です。自分の案件では右の列を書き換え、操作ごとに1枚作ります。入力と応答を並べておくと、たとえば「社員の入力欄に受付番号は要るか」という疑問にも答えられます。

| 決めること | 修理を依頼する場合 |
| --- | --- |
| 誰が何をするか | 利用を許可された社員が、修理してほしい物と場所を届ける |
| どこへどう送るか | `POST /repair-requests`。登録先は依頼の一覧と同じパス |
| 入力の形式と範囲 | `Content-Type: application/json`。本文の例は `{"title":"椅子がぐらつく","location":"第2会議室"}`。どちらも必須で、前後の空白を除いて1〜100文字 |
| 何をもって成功とするか | 1件を保存し、`201 Created` を返す。`Location` は新しい依頼のパス。本文には `id`、`title`、`location`、初期状態を表す `"status":"open"` が入る |
| 失敗した人がどう直せるか | JSON の書き方に誤りがあれば `400`、本文の形式をサポートしていなければ `415`、空白だけの件名なら `422`。アプリは `application/problem+json` で理由を返す |
| どうテストするか | 返された `Location` に `GET` すると、登録した件名と場所が返る。件名が空白だけなら、登録件数は増えない |

HTTP が定めるのは、メソッドや応答コードが伝える意味です。「件名は100文字まで」「初期状態は未完了」という約束は、この業務の判断として記録します。ここを分けておくと、別の業務へ設計を持ち込むときに、どの条件を改めて決めるべきか分かります。[RFC 9110 §15 応答コード](https://www.rfc-editor.org/rfc/rfc9110.html#section-15)・[RFC 9457 §3 エラー本文](https://www.rfc-editor.org/rfc/rfc9457.html#section-3)

記入に迷ったら、[何を1件と数えるか](02-rest.md)、[番号や条件をどこに置くか](03-addresses.md)、[どのメソッドで頼むか](04-methods.md)、[利用者に何を返すか](05-responses.md)の順に見直してください。

## 3．実際の使われ方を確かめる

**誰のデータに触れられますか。** 今回は、利用を許可した社員が共有台帳を操作します。「自分の依頼だけ取り消せる」という業務なら、取り消しの契約に、認証で確かめた利用者と保存した所有者を照合する条件を加えます。

**件数が増えたらどう読みますか。** この一覧では番号の小さい順に既定で20件、最大100件ずつ返します。続きがあれば、画面は応答の `next_after` を次の要求の `after` に渡します。`null` なら終わりです。ページをめくる間にも依頼の状態は変わるので、月末時点の全件を集計したい場合には、読んでいる途中で対象が変わらない仕組みを別に決めます。[Google AIP-158「ページ分割」](https://google.aip.dev/158)

**通信が途切れてもやり直せますか。** 受付の返事が消えた場合、同じ本文をもう一度送ると依頼が2件できることがあります。この教材の登録には重複を防ぐキーがありません。自動再送が必要な業務なら、同じ操作を識別する方法と、その識別子を有効とする期間を契約に加えます。[RFC 9110 §9.2.2 冪等なメソッド](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)・[Amazon Builders’ Library「安全に再試行できる API」](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

**要件を変えたとき、今の利用者はどうなりますか。** たとえば「担当部署」を必須にすると、今の画面からは登録できなくなります。任意の入力として追加し、省略時は従来どおり受け付けるなら、画面を順に更新できます。[Google AIP-180「後方互換性」](https://google.aip.dev/180#adding-components)

待ち時間や処理件数が業務を左右する場合は、「昼休みに何人が送るか」「画面は何秒待てるか」を利用者と決めます。想定する件数と許容する待ち時間を組にして残すと、運用前に同じ条件で測れます。

## 4．別の人が、結果を予測できるか試す

設計メモを画面の担当者に渡し、「件名の前後に空白を入れて送ったら、何が返りますか」「空白だけなら、どこを直しますか」と聞いてみてください。送る要求、返る応答、保存された件数をメモから判断できれば、その例を動作確認に使えます。次の章では、ここで決めた操作を OpenAPI で表します。
