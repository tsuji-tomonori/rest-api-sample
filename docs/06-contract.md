# 第6章　業務の言葉を API の契約にする

「会議室の椅子がぐらつく」と社員が知らせたら、受付番号を渡したい。総務は未完了の依頼を順に見て、修理を終えたら完了を記録したい。この二つの場面から、画面を作る人と API を作る人が共有する約束を決めましょう。この約束を **API の契約** と呼びます。

## 何を送れば、何が返るか

社員が入力するのは修理の件名と場所です。受付番号を付けるのはサーバーの役目です。受付時の状態も、サーバーが `open`（未完了）にそろえます。そこで、登録するときと、結果を見るときのデータを分けます。

| 利用場面 | JSON の例 |
| --- | --- |
| 社員が登録する | `{"title":"椅子がぐらつく","location":"第2会議室"}` |
| 社員が番号を受け取る | `{"id":12,"title":"椅子がぐらつく","location":"第2会議室","status":"open"}` |
| 総務が修理を終える | `{"status":"completed"}` |

件名と場所はどちらも必須です。この教材では前後の空白を取り除き、それぞれ1〜100文字を受け付けます。空白だけの件名では、総務が作業内容を判断できないからです。更新で受け付けるのは `status` だけです。`open` に戻せるので、完了を誤って入力した場合も同じ操作で訂正できます。

## 画面の操作ごとに応答を決める

| したいこと | メソッドとパス | 成功をどう確かめるか |
| --- | --- | --- |
| 依頼を登録する | `POST /repair-requests` | `201 Created`。本文に登録結果、`Location` ヘッダーに個別のパスがある |
| 未完了の依頼を探す | `GET /repair-requests?status=open` | `200 OK`。該当する依頼がなければ `items` は空の配列になる |
| 受付番号で依頼を開く | `GET /repair-requests/{request_id}` | `200 OK`。その番号の依頼が1件返る |
| 対応状況を変える | `PATCH /repair-requests/{request_id}` | `200 OK`。本文の `status` が指定した値になっている |
| 誤って登録した依頼を消す | `DELETE /repair-requests/{request_id}` | `204 No Content`。本文は空になる |

一覧が空なら、検索は成功しています。一方、個別の番号が見つからなければ、この API は `404` を返します。入力した件名が空だった場合や `status` が `done` だった場合は `422` です。アプリのエラー本文は `application/problem+json` として読めます。件名の長さや状態名は業務上の取り決めです。応答コードやエラー本文の形式には HTTP の仕様を使います。[RFC 9110 §15 応答コード](https://www.rfc-editor.org/rfc/rfc9110.html#section-15)・[RFC 9457 §3 エラーの形式](https://www.rfc-editor.org/rfc/rfc9457.html#section-3)

## 一覧の「次へ」を設計する

未完了の依頼が12番、18番、25番の順で並んでいるとします。一度に2件を表示する画面では、次のように読み進めます。表では各依頼の番号だけを示します。

| 画面からの要求 | `items` に含まれる番号 | `next_after` |
| --- | --- | --- |
| `GET /repair-requests?status=open&limit=2` | 12、18 | `18` |
| `GET /repair-requests?status=open&limit=2&after=18` | 25 | `null` |

画面は、サーバーから受け取った `next_after` を次の要求の `after` に渡します。`null` ならそこで終了です。`limit` は1〜100件で、省略すると20件です。`after` に指定できるのは1〜2,147,483,647の整数です。指定した番号より大きい依頼を、番号の小さい順に返します。`status` を省略すると両方の状態が対象になります。

ページをめくる間に12番が消えても、2ページ目は18番の続きから読めます。その間に25番が完了して26番が届けば、2ページ目には新しい26番が現れます。ここでの目的は、総務が**今**対応する依頼を探すことです。月末時点の全件を集計するには、読み取り時点を固定するなど、別の約束が必要です。

この教材は公開する番号と並び順が同じなので、続きの位置を数値で表します。並び順を後から変えたいサービスでは、利用者が中身を解釈せず、そのまま送り返す文字列にする方法もあります。Google の設計指針はこの方式を採っています。どの方式でも、続きを読む間は検索条件をそろえます。[Google AIP-158「ページ分割」](https://google.aip.dev/158#opacity)

## 誰に何を許すか

この例では、利用を許可した社員が同じ修理台帳を扱い、登録から削除までの操作を行えます。AWS では API Gateway が署名を確認し、この API を呼び出す権限があるときに Lambda へ渡します。[AWS「HTTP API の IAM 認可」](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-access-control-iam.html)

要件が「社員は自分の依頼だけ取り消せる」に変わると、操作の権限だけでは判断できません。認証で確かめた利用者を依頼の所有者として記録し、取り消すときに照合する設計が必要です。共有台帳を対象とする今回のサンプルには、この個人別の判定は含めていません。

## 契約を OpenAPI と具体例で残す

OpenAPI は、操作や入力、応答をツールが読める形で記述する仕様です。第7章でアプリを起動すると、ローカルの `/docs` で操作を試し、`/openapi.json` で定義そのものを読めます。まず定義の `paths` から `/repair-requests` の `post` を探してください。`requestBody` から登録時の入力へ、`responses` の `201` から登録結果へたどれます。`$ref` は、別の場所に書いた定義への参照です。[OpenAPI 3.1.1「Operation Object」](https://spec.openapis.org/oas/v3.1.1.html#operation-object)・[FastAPI「First Steps」](https://fastapi.tiangolo.com/tutorial/first-steps/)

設計を見直すときは、変更前の画面の動きを一つ選びます。たとえば「担当部署」の入力を必須にすると、これまでの件名と場所だけの登録が失敗します。任意の項目として追加し、省略時に従来どおり受け付ければ、今の画面を使い続けられます。応答の状態名を増やすときも、画面が新しい値を表示できるか確かめます。[Google AIP-180「後方互換性」](https://google.aip.dev/180#adding-components)

最後に、判定できる言葉で一つ書いてみましょう。「件名の前後に空白を入れて登録する。返ってきた番号で依頼を開くと、空白を除いた件名と `open` が返る」。次の章でこの約束を手元の API で確かめます。
