# 第11章　API のテストを組み立てる

修理依頼の「完了」を押すと、画面には `200 OK` と `"status":"completed"` が返りました。ところが翌朝、同じ依頼を開くと、まだ未完了です。レスポンスだけを見るテストは通っても、保存されていなければ仕事は終わりません。テストを作るときは、**その場で何が返るか**と、**次に何ができるようになるか**を一組にします。

## 設計シートの約束をテストケースにする

**サンプルで試せる**　最初は成功例を一つ選び、結果が変わる境目と失敗例を加えます。修理依頼の設計シートなら、次のように期待結果を書けます。

| 確かめる約束 | 入力や操作の例 | 観察する結果 |
| --- | --- | --- |
| 受付番号から同じ依頼を開ける | 件名と場所を付けて `POST` し、返された `Location` に `GET` | `201` の後に `200`。番号・件名・場所が一致し、状態は `open` |
| 入力の境界を守る | 前後の空白を除いて件名が1文字、100文字、101文字、または空白だけ | 1文字と100文字は受理。101文字と空白だけの件名は入力エラー |
| 失敗しても保存内容を保つ | `open` の依頼に `{"status":"unknown"}` を送る | `422` と `application/problem+json`。同じ番号を読み直すと `open` |
| 一覧の続きを取りこぼさない | 未完了の1、3、4、5番を2件ずつ読む。1ページ目の後で3番を削除 | 最初は1、3番で `next_after` は `3`。次のリクエストに `after=3` を付けると4、5番が読め、最後の `next_after` は `null` |
| 同じ操作を再送したときの結果が分かる | 同じ依頼を2回削除する | 1回目は本文なしの `204`、2回目は `404`。依頼は削除済み |

**設計例（未実装）**　共有台帳を「依頼者本人だけが更新できる」仕組みに変える場合は、同じ依頼を本人と同僚から更新する2ケースを用意します。本人には `200`、同僚には `403` を返す設計なら、拒否された後も元の値が残ることまで確かめます。現行サンプルが AWS で検証するのは、API 自体の呼び出し権限です。

## 見つけたい不具合に合わせて、試す範囲を決める

**サンプルで試せる**　件名の文字数なら、入力モデルを直接呼び出すだけで判断できます。一方、「別の画面から開くと元に戻る」問題を調べるには、リクエストをまたいで保存結果を読み直す必要があります。

| 試す範囲 | このサンプルで見つけられる不具合の例 |
| --- | --- |
| **単体**。入力モデルやエラー処理を直接呼ぶ | 空白を除く前に文字数を数えた。利用者が送った受付番号を受け取ってしまった |
| **FastAPI と SQLite**。一時 DB にテーブルを作り、`TestClient` でルートを呼ぶ | 登録に失敗したのに一覧に行が増えた。ページの続きに同じ依頼が出た |
| **PostgreSQL の権限とマイグレーション**。テスト用 DB に変更を2回適用し、アプリ用の DB 利用者で試す | 2回目の適用で失敗した。アプリから行を更新できない、またはテーブル定義まで変えられる |
| **Compose の HTTP と PostgreSQL**。別コンテナから登録・更新・削除し、別の DB 接続でも行を読む | 更新直後のレスポンスは `completed` でも、DB に変更が確定していない |
| **公開仕様書と実際の API**。YAML に載せた入力を HTTP で送り、実際のレスポンスを照合する | `201` のはずが `200` になった。JSON の型は合うのに、登録した場所と返った場所が違う |

### まず手元で、短いテストから実行する

Python 3.12 と uv がある端末で、リポジトリのルートから実行します。次の3行は順に、入力などの単体テスト、SQLite を使った API のテスト、FastAPI が生成する仕様書と公開 YAML の照合です。

```bash
uv run --locked python -m pytest -q tests/unit
uv run --locked python -m pytest -q tests/test_api.py
uv run --locked python -m package.app.export_openapi --check docs/openapi.yaml
```

仕様書の `--check` が成功すれば、保存した YAML が現在のコードと一致しています。そこから実際に登録できるかは、次のように API を動かして確かめます。Docker と Docker Compose v2 を用意し、同じディレクトリで実行してください。

```bash
docker compose up --build --wait api
docker compose run --rm integration
uv run --locked --group contract python tests/contract/check.py
```

2行目は、社員が修理を依頼し、総務が完了にする流れを試します。登録のレスポンスから得た番号を使い、完了状態が PostgreSQL に残り、削除後は行が消えることまで確認します。3行目はホストの `http://127.0.0.1:8000` へ接続し、公開仕様書と照合します。起動の前提と一時データの片付け方は、[アプリの手順](../package/app/README.md)にあります。

## スキーマが合うことと、業務の答えが合うこと

**サンプルで試せる**　仕様書で「状態は `open` か `completed`」と決めても、登録直後にどちらを返すかは別の約束です。初期状態が誤って `completed` になっていても、どちらも許された文字列なので、レスポンスの型や値の範囲は満たします。

このサンプルの契約テストでは、YAML に載せた登録4例、更新4例を実送信します。Schemathesis でレスポンスがスキーマに合うことを調べ、それぞれの期待ステータスや期待する項目値もテストコードで比べます。登録で得た番号と `Location` を後続のリクエストに使うので、毎回違う番号でも正しい依頼を確認できます。さらに、仕様書が許す状態から生成した値で更新し、読み直した結果も照合します。

## CI の成功から、配信後の疎通確認へ

**サンプルで試せる**　GitHub Actions の `Verify sample` は変更ごとにテストを実行します。PostgreSQL 用のテストには CI 専用の接続先 `TEST_POSTGRES_URL` を渡します。この指定がない手元の実行では、そのテストはスキップされるので、結果の `skipped` も確認します。

AWS への配信を設定した場合、検証に合格した `main` の対象コミットをデプロイし、マイグレーションの完了後に、公開 URL から次の3件を確かめます。

| 公開 URL に送るリクエスト | 期待する結果 |
| --- | --- |
| 署名なしの一覧取得 | API Gateway が `403` で拒否する |
| 署名付きで `?limit=1` の一覧取得 | `200` と一覧の JSON が返る。0件でも正常 |
| 署名付きで `?limit=0` の一覧取得 | `422` と入力エラーの Problem Details が返る |

3件とも読み取りなので、運用中の修理台帳にテスト用の行を増やさずに、入口の権限と保存先までの動作を確認できます。CI 上で AWS のレスポンスを模したテストに合格したことと、実際に配信先へ到達できたことは、記録を分けて読みます。実行結果の見方と、障害を切り分ける手順は[次章の運用](12-operations.md)で扱います。

テストに失敗したら、どこまで通ったかを見ます。`--check` だけが失敗したときは、生成し直した YAML の差分を設計シートと照合します。単体テストが成功して Compose の業務フローだけが失敗したときは、最初に期待と違ったレスポンスを特定し、移行結果と PostgreSQL に残った行を調べます。公開 URL で署名付きの照会だけが `403` なら、入力モデルを直す前に、その呼び出し元の署名と権限を確認します。

## この章で決めたこと

- 成功例、失敗例、境界の入力ごとに、返るステータス・本文と、保存後の状態を決める。
- 入力だけの判定は単体で試し、保存・権限・公開仕様書との一致は、それぞれを確かめられる環境で試す。
- 配信後は読み取りのリクエストで、実際の入口が拒否すべき操作を拒み、許可した操作を完了することを確かめる。
