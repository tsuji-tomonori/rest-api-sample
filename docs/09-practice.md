# 第9章　会議室の予約を設計してみる

修理依頼では、椅子の件名と場所が同じでも、別々の依頼として受け付けました。会議室では事情が違います。同じ部屋を同じ時間に二人が予約できたら、当日、どちらかが使えなくなります。この違いを API の契約に表してみましょう。ここからは自分で設計を試す演習です。

## お題

社内の予定表から、社員が会議室の空きを調べ、予約できるようにします。部屋はあらかじめ登録済みです。

- 社員は部屋と日付を選び、その日の予約時間を確認できます。
- 一つの予約で使うのは1室です。同じ部屋で利用時間が重なったら、先に受け付けた予約を残し、もう一人には別の時間を選んでもらいます。
- 取り消せるのは予約した本人です。

回答例を読む前に、10時から11時まで予約がある部屋を思い浮かべてください。別の人が10時30分から予約したときと、11時ちょうどから予約したときで、画面はどう応答するでしょうか。次の表を設計メモとして使えます。

| 決めること | 自分の案件で書き出す内容 |
| --- | --- |
| 利用者と目的 | 誰が、いつ、何を知るか。何を変更するか |
| 対象と操作 | 1件を見分ける番号、一覧のパス、必要なメソッド |
| 入力と出力 | 利用者が決める値、サーバーが決める値、必須項目 |
| 業務ルールと権限 | 許可する人、値の境界、同時に操作したときの結果 |
| 応答と再送 | 成功・失敗の例、次に取れる行動、返事が途切れた場合の扱い |
| 確認方法 | 入力例と、応答や保存件数から判定できる期待結果 |

## 回答例　予約の単位は「1室の時間枠」

会議室に番号を、予約にも別の番号を付けます。予定を調べるときは部屋が入口です。一度取った予約は、その予約番号で開いたり取り消したりできます。以下はこの業務のために選んだパスです。

| 利用者の行動 | 要求 | 主な成功応答 |
| --- | --- | --- |
| 3番の部屋の予定を見る | `GET /rooms/3/reservations?date=2030-06-12` | `200` とその日に重なる予約の開始・終了時刻。空いていれば空の一覧 |
| 3番の部屋を予約する | `POST /rooms/3/reservations` | `201` と予約内容。`Location` に作成した予約のパス |
| 自分の予約を確認する | `GET /reservations/48` | `200` と予約内容 |
| 自分の予約を取り消す | `DELETE /reservations/48` | `204`。予定表に空きが戻る |

この例の本社は日本にあるので、一覧の `date` は日本時間の1日と決めます。開始と終了は、次のように UTC との時差を含む日時で送ります。`+09:00` は UTC より9時間進んでいることを示します。日付をまたぐ予約も、時間が重なる両方の日の予定表に出します。[RFC 3339 §5.6 日時の表記](https://www.rfc-editor.org/rfc/rfc3339.html#section-5.6)

```json
{
  "starts_at": "2030-06-12T10:00:00+09:00",
  "ends_at": "2030-06-12T11:00:00+09:00"
}
```

部屋はパスで決まります。予約者は認証で確かめた社員から決めます。この設計なら、別の人の名前を本文に書いて予約者になり代わる余地がありません。予約の確認と取り消しでは、サーバーが保存した予約者と、操作中の社員を照合します。一覧には空きを探すために必要な時間だけを載せます。

## 10時30分と11時で何が変わるか

終了時刻を「次の人が使い始められる時刻」と決めます。10時から11時までの予約に対して、10時30分からの予約は重なります。11時からの予約は重なりません。入力が整っていても、直前にほかの人が予約したら結果は変わります。そこで、時間帯が埋まっているときは `409 Conflict` を選びます。画面は予定表を読み直し、空いている時間を案内できます。[RFC 9110 §15.5.10 競合](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.10)

| 確かめる場面 | 期待する結果 |
| --- | --- |
| 開始と終了がともに10時 | `422`。終了を開始より後に直すよう伝え、予約は作らない |
| 10時〜11時に予約がある部屋へ、10時30分〜11時30分を申し込む | `409`。元の予約1件が残る |
| 同じ部屋へ、11時〜12時を申し込む | `201`。前の予約と隣り合う2件になる |
| 空いている部屋の同じ時間に、二人が同時に申し込む | 一方が `201`、もう一方が `409`。保存される予約は1件 |
| 他人の予約番号で取り消す | この例では `404` を返して予約の有無を伏せる。元の予約は残る |

同時予約では、二人の画面がどちらも「空き」と表示する瞬間があります。登録の直前に空きを確認するだけでは、二人とも確認を通過します。保存先を PostgreSQL にするなら、同じ部屋で時間帯が重なる行を保存できない制約を設け、競合した要求に `409` を返せます。[PostgreSQL「時間帯の重複を防ぐ制約」](https://www.postgresql.org/docs/current/rangetypes.html#RANGETYPES-CONSTRAINT)・[RFC 9110 §15.5.4 対象の存在を伏せる場合](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.4)

## 返事だけが届かなかったら

登録直後に通信が途切れたとします。画面には「予約できた」とも「別の人が取った」とも言い切れません。自動再送を要件に加えるなら、画面が予約操作ごとに一意の識別子を作り、再送時も同じ値を送る方法があります。サーバーは社員・識別子・申込内容・結果を予約と一緒に保存します。初回と同じ申込なら同じ予約番号を返し、識別子だけを使い回した別の申込はエラーにします。識別子を何時間保管するかも、再送できる期限として利用者に伝えます。[Amazon Builders’ Library「Making retries safe with idempotent APIs」](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

自分の案件に置き換えるときも、最初の一行は「誰が、何に困っているか」です。そこから操作を一つ選び、成功する例と、判断が分かれる境界の例を書いてください。チームの誰が試しても同じ結果を期待できれば、その例をそのまま受け入れテストに使えます。
